# 第 19 章 · 状态机与工作流编排 — 数据结构原理

> 本章涉及 4 种数据结构：**图（状态转移图）**、**栈（推理链）**、**队列（任务队列）**、**树（思维树）**，外加 **哈希表（状态存储）**。
> 它们在 AI 智能体（agent）的工作流编排中各司其职，协作完成「状态驱动 → 推理循环 → 任务执行 → 思维搜索」的全流程。

---

## 1. 图（状态转移图）— 状态机的骨架

### 1.1 基本概念

有限状态机（Finite State Machine, FSM）是建模「状态 + 转移」的经典数学结构：

```
FSM = (S, Σ, δ, s₀, F)
  S   : 状态集合（有限）
  Σ   : 输入字母表（事件 / 条件）
  δ   : 转移函数 S × Σ → S
  s₀  : 初始状态
  F   : 终止状态集合
```

把 FSM 看成图：
- **节点** = 状态
- **边** = 状态转移（带条件）
- **条件转移** = 带守卫函数（guard）的边

```
    has_input        plan_ready       action_done
    idle ────────→ planning ────────→ acting ────────→ observing
     ▲                                              │
     │              need_more_steps                 │
     │              ┌───────────────────────────────┘
     │              ▼
     │           acting ←─────────── observing
     │                                  │
     │              task_complete       │  has_error
     │              ┌───────────────────┘
     │              ▼
     │            done                 error
     │                                  │
     └────────────── retry ─────────────┘
```

### 1.2 为什么 agent 工作流是状态机

AI 智能体的工作流天然是状态机：

| 状态 | 含义 | 进入条件 | 离开条件 |
|------|------|----------|----------|
| idle | 等待用户输入 | 启动 / 重试 | 收到输入 |
| planning | 生成计划 | 收到输入 | 计划生成完 |
| acting | 执行动作 | 计划就绪 | 动作执行完 |
| observing | 观察结果 | 动作完成 | 决定继续 / 完成 / 出错 |
| done | 任务完成 | 观察到完成信号 | — |
| error | 出错 | 观察到错误 | 重试 |

把工作流建模为状态机的好处：
- **可可视化**：状态转移图一目了然，便于调试和理解
- **可维护**：新增状态只需 `add_transition`，不改运行逻辑
- **可并行**：独立的状态分支可以并行执行
- **可中断**：任何状态都可以暂停、恢复、回滚

### 1.3 状态转移图的存储

状态转移图用**邻接表**存储最自然：

```python
graph: dict[str, list[Transition]] = {}
# graph["idle"] = [Transition("idle", "planning", "has_input", guard_fn)]
```

每个状态对应一个 `Transition` 列表，转移时遍历出边找第一个 `guard` 满足的。这就是 LangGraph 的 `add_conditional_edges` 语义。

### 1.4 状态存储：哈希表

状态机的「当前状态 + 所有状态变量」用一个**哈希表**（dict）存储：

```python
state: dict[str, object] = {
    "current": "planning",   # 当前状态
    "has_input": True,       # 状态变量
    "plan_ready": False,
    "steps_done": 3,
    ...
}
```

这就是 LangGraph 的 **state dict**——所有节点共享读写同一个状态字典，节点间通过状态变量传递信息。哈希表的选择是因为：
- **O(1) 读写**：状态变量按名访问
- **动态 schema**：不同节点可以往 state 里塞不同字段
- **可序列化**：dict 天然可以 JSON 序列化，用于持久化 / 跨进程传递

## 2. 栈 — ReAct 推理链的回溯

### 2.1 ReAct 模式

ReAct（Reasoning + Acting）是 agent 最经典的推理模式，每一步：

```
think    : LLM 推理，决定下一步做什么
  ↓
act      : 执行动作（调用工具 / 检索 / 计算）
  ↓
observe  : 观察动作结果
  ↓
（循环，直到得出答案）
```

一个完整的 ReAct 轨迹：

```
think #1: 任务=计算巴黎人口+100万，需要先查巴黎人口
act   #2: search(巴黎人口)
observe #3: 巴黎人口约 210 万
think #4: 210 万 + 100 万 = 310 万，但需要验证单位
act   #5: calculate(210 + 100)
observe #6: 310
think #7: 单位是万，所以答案是 310 万
act   #8: format_answer(310万)
observe #9: 格式错误：缺少单位说明    ← 出错！
```

### 2.2 为什么推理链用栈

推理链用**栈**而不是列表 / 队列，关键在于**回溯能力**：

```
出错时：
  栈：pop 出错的 act + observe（2 步），从上一个 think 重新推理
  无栈：只能从头重跑整个流程（12 步）
```

栈的 LIFO 特性正好匹配「最近的一步最可能需要撤销」：
- `push(think/act/observe)`：每步压栈
- `pop()`：回溯撤销最近一步
- `top()`：查看当前步，决定下一步

### 2.3 嵌套子任务的栈

栈还支持**嵌套子任务**。主任务执行到一半发现需要先解决一个子问题：

```
主任务 think → act → [发现需要子任务]
  压栈：子任务 think → act → observe → think → ... → 答案
  弹栈：回到主任务，用子任务结果继续
```

栈的深度 = 嵌套层数。这是递归推理的自然结构，列表 / 队列无法表达嵌套。

### 2.4 栈 vs 无栈的代价

| 能力 | 栈 | 无栈线性 |
|------|----|----------:|
| 回溯 | `pop()` O(1) | 不支持 |
| 出错恢复 | 2 步（pop + 重推理） | 12 步（重跑全流程） |
| 嵌套子任务 | 压栈 / 弹栈 | 无法表达 |
| 内存 | O(推理深度) | O(总步数) |

栈的代价是多了一层抽象，但换来回溯和嵌套能力——这是 agent 处理复杂、易出错任务的关键。

## 3. 队列 — Plan-and-Execute 的任务调度

### 3.1 Plan-and-Execute 模式

复杂任务先**拆解**再**执行**：

```
planner  : LLM 把大任务拆成有序子任务列表
  ↓
executor : 逐个执行子任务，收集结果
  ↓
replan   : 执行结果不理想时，动态重新规划
```

示例：

```
任务：写一篇关于 X 的研究报告
planner 生成：
  1. 理解问题
  2. 收集数据
  3. 分析数据
  4. 生成方案
  5. 验证方案
executor 逐个执行（FIFO）...
执行到第 3 步发现数据不够 → replan：追加 "3.5.补充数据" "3.6.交叉验证"
```

### 3.2 为什么任务列表用队列

任务列表用**队列（FIFO）**而不是栈（LIFO），关键在于**依赖顺序**：

```
计划：1.理解 → 2.收集 → 3.分析 → 4.生成 → 5.验证

队列(FIFO)：1 → 2 → 3 → 4 → 5  ✓ 按计划顺序，依赖正确
栈  (LIFO)：5 → 4 → 3 → 2 → 1  ✗ 反序，先验证再理解，依赖全乱
```

planner 生成的任务有**依赖关系**：后面的任务依赖前面的结果。FIFO 保证先规划的任务先执行，依赖顺序正确。

### 3.3 动态重新规划

队列支持**动态入队**：执行中发现新任务，`append` 到队尾：

```python
def replan(self, new_tasks: list[str]) -> None:
    for name in new_tasks:
        self.queue.append(Task(name))  # 追加到队尾
```

这是 Plan-Execute 区别于静态流水线的核心能力——执行中根据结果动态调整计划。队列的「队尾入队、队头出队」正好匹配「新任务排到后面、先规划的任务先执行」。

### 3.4 队列 vs 栈的代价

| 能力 | 队列 (FIFO) | 栈 (LIFO) |
|------|------|------:|
| 执行顺序 | 按计划顺序 | 反序 |
| 依赖正确 | ✓ | ✗ |
| 动态重规划 | append 到队尾 | push 到栈顶（会先执行） |
| 公平性 | 先来先服务 | 后来先服务 |

栈做 Plan-Execute 的问题：动态重规划时新任务 `push` 到栈顶，会**立即执行**，打断当前流程；队列 `append` 到队尾，新任务**排到后面**，不打断当前执行。

## 4. 树 — Tree-of-Thought 的分支搜索

### 4.1 Tree-of-Thought 模式

复杂推理时，不只走一条思维链，而是**分支多个方向**，评估每个方向的潜力，搜索最优思维路径：

```
                    根问题
                  /    |    \
              分支1   分支2   分支3
              /  \    |    /  \
           d2-1 d2-2 d2-1 d2-1 d2-2
            ...
```

每一步：
1. **生成**：当前思维展开 k 个候选下一步
2. **评估**：给每个候选打分
3. **剪枝**：低分分支直接砍掉
4. **搜索**：BFS / DFS 遍历思维树找最优叶

### 4.2 为什么思维搜索用树

思维搜索用**树**而不是线性列表，因为：

- **层次结构**：思维从粗到细，第 1 层是大方向，第 2 层是具体方案，第 3 层是细节……天然形成树
- **分支**：每个思维节点有多个候选下一步，需要全部探索
- **剪枝**：低分子树整棵砍掉，不展开——树结构让「砍子树」是 O(1) 的标记
- **回溯**：DFS 用栈回溯，BFS 用队列逐层，都依赖树结构

### 4.3 BFS vs DFS 搜索思维树

```
BFS（广度优先）：用队列，逐层搜索
  优点：找浅层最优解快
  缺点：内存 O(宽度^深度)，深树爆炸

DFS（深度优先）：用栈，一条路走到底再回溯
  优点：内存 O(深度)，深树友好
  缺点：可能深挖一个差分支
```

ToT 通常用 **BFS + 评分 + 剪枝**（beam search 变体）：每层保留 top-k 高分节点，其余剪枝。这平衡了广度和深度。

### 4.4 剪枝的价值

剪枝是 ToT 高效的关键。设 `branching=3, max_depth=4`：

```
不剪枝：3^4 = 81 个叶节点，全展开 1+3+9+27+81 = 121 节点
剪枝（阈值 0.3，约剪掉 30%）：展开 ~40 节点，节省 ~67%
```

剪枝让搜索空间从指数爆炸降到可控规模。树结构让剪枝是「标记子树不展开」，O(1) 操作。

### 4.5 树 vs 线性的代价

| 能力 | 树 | 线性枚举 |
|------|----|----:|
| 分支探索 | ✓ | ✗（只走一条路） |
| 剪枝 | 标记子树 O(1) | 不支持 |
| 找最优解 | BFS/DFS 搜索 | 枚举所有可能 |
| 内存 | O(分支×深度) | O(候选总数) |

线性枚举要遍历所有可能才能找最优，树 + 剪枝只展开有潜力的分支，搜索空间指数级缩小。

## 5. 四种数据结构如何协作

### 5.1 各司其职

```
用户提问
  │
  ▼
[图/状态转移图]  StateMachine：状态机驱动状态转移
  │                idle→planning→acting→observing→done
  │                决定「现在该做什么」
  ▼
[栈]             ReActLoop：think→act→observe 推理链
  │                在 acting 状态内，用栈记录推理 + 回溯
  │                决定「这一步具体怎么做」
  ▼
[队列]           PlanAndExecute：planner 生成任务队列
  │                在 planning 状态，把任务拆成有序子任务
  │                executor FIFO 执行，支持 replan
  ▼
[树]             TreeOfThought：多分支思维搜索
  │                在 think 步骤，分支多个思维方向
  │                BFS/DFS + 剪枝找最优
  ▼
[哈希表]         状态存储：state dict
  │                所有节点共享读写状态变量
  │                LangGraph 的 state dict
  ▼
输出答案
```

### 5.2 协作的层次

四种数据结构在**不同层次**解决问题：

| 层次 | 数据结构 | 解决什么 | 对应模式 |
|------|----------|----------|----------|
| 工作流层 | 图 | 状态转移拓扑 | LangGraph StateGraph |
| 推理层 | 栈 | 单步推理 + 回溯 | ReAct |
| 任务层 | 队列 | 任务拆解 + 调度 | Plan-and-Execute |
| 思维层 | 树 | 多分支搜索 | Tree-of-Thought |
| 存储层 | 哈希表 | 状态变量共享 | state dict |

它们不是替代关系，而是**嵌套关系**：
- 状态机（图）的某个状态内，可以跑 ReAct 循环（栈）
- ReAct 的 think 步骤，可以用 ToT（树）搜索多个思维方向
- Plan-Execute（队列）的每个任务，本身可以是一个子状态机
- 所有结构共享同一个 state dict（哈希表）

### 5.3 数据结构间的信息流动

```
用户输入 → [哈希表] state["input"] = question
              │
              ▼
[图] 状态机读 state，决定转移到 planning
              │
              ▼ state["current"] = "planning"
[队列] planner 读 state["input"]，生成任务队列 [t1, t2, t3, ...]
              │
              ▼ 逐个 execute
[栈] 每个任务内跑 ReAct：think→act→observe 压栈
              │
              ▼ think 步骤
[树] ToT 分支多个思维，BFS+剪枝找最优 thought
              │
              ▼ 最优 thought 写回 state
[栈] 用最优 thought 继续 act→observe
              │
              ▼ 任务完成，队列出队下一个
[队列] 继续下一个任务...
              │
              ▼ 所有任务完成
[图] 状态机转移到 done
              │
              ▼
输出答案
```

## 6. 小结

本章四种数据结构在 AI 智能体工作流中协作：

1. **图（状态转移图）**：状态机的骨架，邻接表存转移拓扑，条件转移用守卫函数，对应 LangGraph StateGraph
2. **栈（推理链）**：ReAct 的回溯结构，LIFO 匹配「最近一步最可能撤销」，支持嵌套子任务
3. **队列（任务队列）**：Plan-Execute 的调度结构，FIFO 保依赖顺序，支持动态 replan 入队
4. **树（思维树）**：ToT 的分支搜索结构，BFS/DFS + 剪枝找最优思维，指数级缩小搜索空间
5. **哈希表（状态存储）**：state dict，所有节点共享读写，O(1) 访问，可序列化

它们分别解决工作流、推理、任务、思维、存储五个层面的问题，通过 state dict 传递信息，嵌套组合完成复杂 agent 工作流。生产级的 LangGraph、AutoGen、CrewAI 都在这五个方向上做了工程化实现。
