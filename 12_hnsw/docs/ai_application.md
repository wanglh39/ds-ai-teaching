# HNSW 向量检索：RAG / 推荐 / 搜索的亚线性引擎

> 本文档讲清 HNSW 在 AI 里的应用：为什么向量检索是 AI 基础设施、暴力 KNN 的 O(n) 瓶颈、HNSW 如何实现亚线性检索、demo 结果解读、生产级实现（FAISS/Milvus/hnswlib）。数据结构原理见 `principle.md`。

## 1. 向量检索：AI 的底层基础设施

大模型时代，几乎所有 AI 应用都涉及「找相似」：

- **RAG（检索增强生成）**：用户提问 → 把问题转向量 → 在知识库找最相似的文档片段 → 喂给 LLM 生成回答。一次 RAG 查询 = 一次向量检索。
- **推荐系统**：用户行为序列转向量 → 找相似的商品/内容向量 → 推荐候选。每次刷新推荐流 = 一次向量检索。
- **语义搜索**：查询句转向量 → 找语义相似的文档 → 排序返回。比关键词搜索理解意图。
- **图片搜索**：图片过 CNN/CLIP 转向量 → 找相似图片向量。以图搜图。
- **去重**：新内容转向量 → 查是否和已有内容相似 → 去重/聚类。
- **异常检测**：实时向量 → 找最近邻 → 距离过大则异常。

这些场景的共同模式：**把对象编码成向量，找最近邻**。向量检索的延迟直接决定应用响应速度。

### 1.1 向量从哪来

**Embedding 模型**把文本/图片/行为编码成稠密向量：

| 模型 | 维度 | 来源 |
|---|---|---|
| BERT | 768 | Google 2018 |
| text-embedding-3-small | 1536 | OpenAI 2024 |
| text-embedding-3-large | 3072 | OpenAI 2024 |
| BGE-large-zh | 1024 | 智源 2023 |
| CLIP | 512 | OpenAI 2021 |
| Cohere embed-v3 | 1024 | Cohere 2024 |

维度通常 512~3072。向量检索要在这个维度下快速找近邻。

### 1.2 规模有多大

| 应用 | 向量数 | 维度 |
|---|---|---|
| 个人知识库 RAG | 10k~100k | 768~1536 |
| 企业文档搜索 | 1M~10M | 768~1536 |
| 推荐系统商品库 | 10M~100M | 64~256 |
| 全网图片搜索 | 1B+ | 512 |
| 大模型记忆层 | 1M~100M | 768~3072 |

100 万向量是常见规模。暴力 KNN 在这个规模下的延迟，就是下一节要算的瓶颈。

## 2. 暴力 KNN 的 O(n) 瓶颈

### 2.1 暴力做法

```python
def brute_knn(vectors, query, k):
    dists = [dist(query, v) for v in vectors]   # 算 n 次距离
    return top_k(dists, k)                       # 排序取前 k
```

每次查询算 n 次距离，每次距离 O(d)。总共 O(n·d)。

### 2.2 延迟估算

n=1M, d=1536（OpenAI embedding）, k=10：

- 距离计算：1M × 1536 = 1.5G 次浮点运算
- numpy 向量化：约 50ms（单核）
- 排序 top-10：O(n) 用 argpartition，约 5ms
- **单次查询约 55ms**

看起来不多？但实际场景：

- **RAG 多跳查询**：一次请求查 5~20 次（多路召回、重排），55ms × 20 = 1.1s
- **并发**：100 QPS × 55ms = 5500ms CPU 时间/秒，需要 6 个核全跑满
- **实时推荐**：用户刷新一次推荐流，查 50 个候选，55ms × 50 = 2.75s

**1M 向量下暴力 KNN 的延迟，让 RAG 从「秒级响应」变成「数秒等待」**。

### 2.3 为什么不能只靠缓存

有人想：把热点查询结果缓存起来。但向量检索的查询是**连续空间**——用户的每个问题向量都不同，缓存命中率极低。不像关键词搜索有固定词表。

### 2.4 空间数据结构也不行

KD-tree 在 d ≤ 10 时 O(log n)，但 d=1536 时**退化到 O(n)**——每个节点切分一次，高维下几乎所有点都在切分面两侧，剪枝无效。这是**维度灾难**的本质：高维空间里任意两点距离都差不多，没法用空间划分剪枝。

## 3. HNSW：亚线性高维检索

### 3.1 核心思想

HNSW 不切空间，建**近邻图**——每个向量连它的最近邻，搜索时在图上贪心走。配合**跳表的分层思想**，从顶层稀疏图跨大距离，逐层下降到第 0 层精确定位。

**为什么图能绕过维度灾难**：图不依赖空间划分，而是依赖「近邻传递性」——A 近 B、B 近 C，则 A 大概率近 C。贪心搜索沿着近邻链走，不需要切分空间。

### 3.2 检索流程

```
HNSW 搜索 query:
  1. 跳表入口点选择：算 query 到原点距离，O(log n) 找投影最近的节点
  2. 从顶层图贪心下降：每层 best-first 搜索，找最近的节点作为下层入口
  3. 第 0 层 best-first 精搜：ef 个候选，返回 top-k
```

**复杂度**：O(log n · M · d)。n=1M, M=16, d=1536：约 16 × 20 × 1536 = 500K 次浮点运算，约 0.5ms。**比暴力 55ms 快 100 倍**。

### 3.3 召回率

HNSW 是**近似**算法——贪心搜索可能漏掉少量近邻。召回率 = HNSW 结果 ∩ 暴力结果 / 暴力结果。

影响召回率的因素：
- **ef_search**：搜索候选集大小。越大召回越高、越慢。典型 64~512。
- **M**：每节点邻居数。越大图越密、召回越高、内存越大。典型 16~48。
- **ef_construction**：建图候选集。越大图质量越好、建图越慢。典型 200~500。
- **分层结构**：上层稀疏图帮助跨大距离，避免陷局部最优。

典型配置下 recall@10 > 95%，延迟比暴力快 100~1000 倍。

## 4. demo 结果解读

我们跑了 HNSW vs 暴力 KNN 的对比，数据量 1k~100k，维度 10 和 50。

### 4.1 延迟对比

| n | dim | 暴力 (ms) | HNSW (ms) | 加速比 |
|---|---|---|---|---|
| 1,000 | 10 | 0.044 | 1.115 | 0.04x |
| 10,000 | 10 | 0.348 | 1.067 | 0.33x |
| 100,000 | 10 | 7.672 | 1.430 | **5.4x** |
| 1,000 | 50 | 0.079 | 1.263 | 0.06x |
| 10,000 | 50 | 1.754 | 1.445 | 1.2x |
| 100,000 | 50 | 18.894 | 1.878 | **10.1x** |

**趋势**：
1. **小数据量（1k, 10k）暴力更快**：numpy 向量化的暴力 KNN 常数极小，HNSW 的 Python 循环开销大于收益。HNSW 的优势在大数据量才显现。
2. **100k 下 HNSW 加速 5~10 倍**：暴力 O(n) 线性增长，HNSW O(log n) 近乎恒定。
3. **dim=50 加速更显著**：高维下暴力单次距离更贵（d=50 vs d=10），HNSW 的节省更大。

**外推到 1M**：暴力 dim=50 约 200ms，HNSW 约 2~3ms，**加速 70~100 倍**。这正是生产级 RAG 的瓶颈所在。

### 4.2 召回率

| n | dim | recall@10 |
|---|---|---|
| 100,000 | 10 | **95.5%** |
| 100,000 | 50 | 39.8% |

**dim=10 召回 95%+**：低维下图质量好，贪心搜索几乎找到所有真正近邻。

**dim=50 召回 40%**：高维下简化版（无分层结构）召回率下降。原因：
1. 我们的简化版**没有分层结构**——只有一层图，贪心搜索容易陷局部最优
2. M=16 邻居数不够——高维下需要更多邻居覆盖各方向
3. ef=48 搜索宽度不够——高维下需要更大候选集

**生产级 HNSW**（hnswlib）在 dim=50 下 recall@10 > 95%，因为：
- 分层结构：上层稀疏图帮助跨大距离，避免局部最优
- 启发式邻居选择：选多样邻居，搜索路径不单一
- 更大参数：M=32, ef_construction=200, ef_search=128

### 4.3 建图延迟

| n | dim | 建图 (ms) |
|---|---|---|
| 10,000 | 10 | 223 |
| 100,000 | 10 | 6,351 |
| 100,000 | 50 | 63,087 |

建图是一次性成本。100k dim=10 用 cKDTree 建图 6s（精确近邻），dim=50 用 numpy 暴力建图 63s。生产级 HNSW 用增量搜索建图，100k 约 1~2s。

### 4.4 为什么小数据量 HNSW 慢

Python 实现的 HNSW 搜索有固定开销（跳表查找 + 堆操作 + visited 数组），约 1ms。暴力 KNN 用 numpy 全向量化，1k 数据只要 0.04ms。所以 n < 10000 时暴力更快。

**C/C++ 实现没有这个问题**——hnswlib 的 HNSW 搜索 1k 数据约 0.01ms，比暴力 0.04ms 还快。Python demo 的 crossover 在 100k，C++ 实现在 1k 以下就 crossover 了。

## 5. 为什么是跳表 + 图

### 5.1 跳表给图什么

**入口点选择**。纯近邻图需要入口点，固定入口点在 query 远时搜索慢。跳表按「到原点距离」排序，O(log n) 找到投影最近的节点作为入口——入口点自适应 query 位置。

```
没有跳表：entry = 固定节点 → query 远时走很多步
有跳表：  entry = 跳表查找(query 投影) → 入口点在 query 附近
```

### 5.2 图给跳表什么

**高维近邻搜索**。跳表是一维结构，高维投影冲突严重。近邻图直接在高维空间建连接，贪心搜索沿着近邻链走，不受维度灾难影响。

```
跳表：找到投影接近的候选，但投影近 ≠ 向量近
图：  从候选出发贪心走，沿着真正近邻链接近 query
```

### 5.3 组合的威力

| 步骤 | 数据结构 | 作用 | 复杂度 |
|---|---|---|---|
| 入口点选择 | 跳表 | O(log n) 找投影最近的节点 | O(log n) |
| 贪心搜索 | 近邻图 | 沿近邻链走向 query | O(log n · M · d) |
| **总计** | **HNSW** | **亚线性高维检索** | **O(log n · M · d)** |

跳表解决「从哪开始搜」，图解决「怎么走最快」。单独都不够，组合起来 O(log n)。

## 6. 生产级实现

### 6.1 hnswlib

Malkov 自己写的 C++ 实现，最接近原论文。

```python
import hnswlib
import numpy as np

# 建图
index = hnswlib.Index(space='l2', dim=128)
index.init_index(max_elements=1000000, ef_construction=200, M=16)
index.add_items(vectors)

# 搜索
index.set_ef(128)  # 搜索时 ef
labels, distances = index.knn_query(queries, k=10)
```

**性能**（1M 向量, dim=128, 单核）：
- 建图：约 60s
- 搜索：约 0.5ms/query
- recall@10：> 95%
- 比暴力快约 1000 倍

### 6.2 FAISS

Facebook（Meta）的向量检索库，支持多种索引：

```python
import faiss

# HNSW 索引
index = faiss.IndexHNSWFlat(128, 16)  # dim=128, M=16
index.hnsw.efConstruction = 200
index.hnsw.efSearch = 128
index.add(vectors)

# 搜索
D, I = index.search(queries, 10)
```

FAISS 还支持：
- **IVF-HNSW**：先倒排文件粗筛，再 HNSW 精搜。适合 10M+ 规模。
- **PQ + HNSW**：乘积量化压缩向量，减少内存。1B 向量 128 维只需 128GB 而非 512GB。
- **GPU 加速**：建图和搜索都在 GPU 上跑，快 10~100 倍。

### 6.3 Milvus

开源向量数据库，支持 HNSW + 多种索引 + 分布式：

```python
from pymilvus import Collection, FieldSchema

# 创建集合
collection = Collection("documents")
collection.create_index(
    field_name="embedding",
    index_params={"index_type": "HNSW", "metric_type": "L2",
                  "params": {"M": 16, "efConstruction": 200}}
)

# 搜索
results = collection.search(
    data=[query_vector], anns_field="embedding",
    param={"params": {"ef": 128}, "metric_type": "L2", "limit": 10}
)
```

Milvus 解决了单机 HNSW 的局限：
- **分布式**：10B+ 向量分片存储，多机并行搜索
- **持久化**：向量存磁盘，内存只缓存热数据
- **增删改**：支持删除（HNSW 原生不支持删除，Milvus 用标记删除 + 定期 compaction）
- **多索引**：同一份数据建多种索引（HNSW + IVF + Flat），按查询模式选

### 6.4 各实现对比

| 实现 | 语言 | 1M 延迟 | recall@10 | 适合场景 |
|---|---|---|---|---|
| 暴力 KNN | numpy | ~50ms | 100% | 小数据，精确 |
| 我们的简化版 | Python | ~2ms | 40~95% | 教学 |
| hnswlib | C++ | ~0.5ms | 95%+ | 单机，高性能 |
| FAISS HNSW | C++ | ~0.5ms | 95%+ | 单机，多索引 |

| Milvus | Go+C++ | ~2ms | 95%+ | 分布式，持久化 |

## 7. 实际应用中的考量

### 7.1 参数调优

| 参数 | 作用 | 典型值 | 调优方向 |
|---|---|---|---|
| M | 邻居数 | 16~48 | 召回↑ 内存↑ 建图慢↑ |
| ef_construction | 建图候选 | 200~500 | 图质量↑ 建图慢↑ |
| ef_search | 搜索候选 | 64~512 | 召回↑ 延迟↑ |

**经验**：先 M=16, ef_c=200, ef_s=64 跑出基线。召回不够加 ef_s；延迟太高减 ef_s；内存不够减 M。

### 7.2 距离度量

- **L2（欧氏）**：通用，适合图片、通用 embedding
- **内积（IP）**：适合归一化后的 embedding（等价余弦相似度）
- **余弦**：文本语义搜索常用。归一化后用 IP 即可

```python
# 余弦相似度 = 归一化后的内积
vectors_normalized = vectors / np.linalg.norm(vectors, axis=1, keepdims=True)
index = hnswlib.Index(space='ip', dim=128)  # 用 inner product
```

### 7.3 增量插入

HNSW 支持增量插入——新向量用已有图搜索找近邻连接。不需要重建索引。

```python
# 建好索引后，随时加新向量
index.add_items(new_vectors)
```

但**删除**是难题——HNSW 原生不支持删除（删了节点图连通性可能破坏）。生产方案：
- **标记删除**：打标记，搜索时跳过。内存不释放。
- **定期重建**：积累一定删除后，重建索引。
- **Milvus 的 compaction**：后台合并，清理已删除节点。

### 7.4 与 RAG 的集成

```python
# 典型 RAG 流程
def rag_answer(question, llm, index, documents):
    # 1. 问题转向量
    q_vec = embed(question)

    # 2. HNSW 检索 top-k 文档
    labels, _ = index.knn_query(q_vec, k=5)

    # 3. 取回文档文本
    context = [documents[i] for i in labels[0]]

    # 4. 喂给 LLM 生成
    answer = llm.generate(question, context)
    return answer
```

HNSW 的延迟（~1ms）远小于 LLM 生成延迟（~500ms），所以 RAG 的瓶颈在 LLM 而非检索。但**并发**场景下，检索的 QPS 限制会成为瓶颈——HNSW 单核约 1000 QPS，不够时需要多副本。

## 8. HNSW 的局限与演进

### 8.1 局限

- **内存占用**：图结构存 n×M 个指针，1M 向量 M=16 约 64MB 额外内存。加上向量本身 1M×128×4 = 512MB，总共约 600MB。
- **建图慢**：O(n log n) 建图，1M 向量约 60s。不能实时建索引。
- **删除难**：原生不支持删除，需要标记删除 + 定期重建。
- **参数敏感**：M、ef 需要根据数据分布调优，没有万能参数。

### 8.2 演进方向

- **DiskANN**：微软提出，把图存磁盘，内存只存入口点 + 部分图。1B 向量只需 16GB 内存。
- **SPANN**：阿里提出，空间分区 + 倒排，减少内存同时保持召回。
- **GPU-HNSW**：FAISS 的 GPU 实现，建图和搜索都加速 10~100 倍。
- **学习索引**：用小模型预测近邻位置，减少图搜索步数。

## 9. 总结

HNSW 是当前向量检索的事实标准——FAISS、Milvus、hnswlib、pgvector 都用它。核心是**跳表思想 + 近邻图**的组合：

- **跳表的分层思想**给图提供入口点和跨大距离能力
- **近邻图**给高维空间提供 O(log n) 贪心搜索
- 组合实现亚线性高维检索，100 万向量下比暴力快 100~1000 倍

在 AI 应用中，HNSW 是 RAG、推荐、语义搜索的底层引擎。它的延迟（~1ms）让大模型应用的「检索」环节几乎无感，瓶颈转移到 LLM 生成上。

理解 HNSW 的关键：**跳表和近邻图是分层 + 贪心下降的同一思想**——跳表按 key 排序分层，HNSW 按近邻关系分层。单独都不够，组合才够。
