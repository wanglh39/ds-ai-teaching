# 第 17 章 · 数据管道与流式处理 — AI 应用

> AI 场景：训练数据的流式加载、滑动窗口统计、近似去重。
> 数据结构：队列 + 环形缓冲 + 树状数组（BIT）+ 布隆过滤器协作。

---

## 1. AI 训练数据加载的瓶颈

### 1.1 问题：数据加载跟不上 GPU

现代 AI 训练的瓶颈常不在 GPU 计算，而在**数据加载**。GPU 算力每秒可处理数百个 batch，
但如果数据加载（读盘 → 解码 → 预处理 → 增强）跟不上，GPU 就会空等（idle）。

```
理想：  GPU 一直忙 → 利用率 ~100%
实际：  GPU 算完一个 batch，等数据 → 利用率 50% 甚至更低
```

瓶颈来源：
- **磁盘 I/O**：高分辨率图像 / 长文本从磁盘读取慢
- **解码**：JPEG/PNG 解码、tokenization 都是 CPU 密集
- **预处理**：归一化、resize、裁剪
- **数据增强**：随机翻转、颜色抖动、mixup 等

### 1.2 解决：多阶段管道 + 并行

把数据加载拆成多阶段，用队列连接，多线程/多进程并行：

```
producer (读盘)  →  processor (解码)  →  augmenter (增强)  →  batcher (组 batch)
   ↑                    ↑                    ↑                    ↑
  I/O 密集            CPU 密集             CPU 密集             内存操作
```

各阶段用独立线程/进程跑，I/O 与 CPU 重叠，GPU 不再空等。

这就是**数据管道**（data pipeline）的核心思想。PyTorch 的 `DataLoader(num_workers=N)`、
TensorFlow 的 `tf.data.Dataset.prefetch(N)` 都是这一模式的实现。

### 1.3 队列在管道中的作用

队列在管道中扮演**阶段间缓冲区**：

- **解耦**：上游不用等下游，下游不用等上游
- **并行**：各阶段独立线程，通过队列传递数据
- **背压**：有界队列满了上游就等/丢，防止 OOM
- **平滑**：吸收各阶段速度波动（突发快/慢）

没有队列，各阶段只能串行：读一个 → 解码一个 → 增强一个 → 组一个 batch，GPU 空等。
有了队列，各阶段重叠：读第 100 个时，解码第 99 个，增强第 98 个，GPU 算第 97 个 batch。

## 2. 流式处理的需求

### 2.1 为什么需要流式？

传统批处理（batch processing）：把所有数据加载到内存，再处理。问题：
- **内存不够**：TB 级数据集无法全装入内存
- **延迟太高**：等所有数据加载完才开始训练，首个 batch 延迟大
- **无法在线学习**：在线学习需要数据来了就处理

流式处理（stream processing）：数据像水流一样，来了就处理，处理完就丢（或归档）。
- 内存固定：只保留当前窗口的数据
- 首个 batch 快：数据来了就开始处理
- 支持在线学习：数据持续流入，模型持续更新

### 2.2 流式训练的典型场景

- **大模型预训练**：互联网级语料（数百 TB），无法全装入内存，必须流式
- **在线学习**：用户行为数据持续流入，模型实时更新
- **增量训练**：新数据来了就接着训练，不用从头来
- **强化学习**：环境交互产生的数据流式进入 replay buffer

### 2.3 环形缓冲在流式处理中的角色

流式处理需要「保留最近 N 个数据」的滑动窗口，环形缓冲天然适合：

- **replay buffer**（强化学习）：保留最近 N 个 transition，旧的被覆盖
- **loss 监控窗口**：保留最近 N 步的 loss，用于早停、学习率调整
- **梯度统计窗口**：保留最近 N 步的梯度范数，用于梯度裁剪阈值自适应
- **数据分布监控**：保留最近 N 个样本的某个特征，检测分布漂移

环形缓冲的优势：
- **内存固定**：预分配定长数组，不随数据流入增长
- **O(1) 写入**：写指针取模，覆盖最老，无需移动数据
- **无需 GC**：覆盖即丢弃，不产生垃圾对象

## 3. 滑动窗口统计

### 3.1 为什么需要窗口统计？

训练过程中，单步的 loss / 梯度波动大（受 batch 内样本影响），不能只看单步。
需要**窗口内统计**才能判断训练趋势：

- **最近 N 步的平均 loss**：判断是否收敛、是否过拟合
- **最近 N 步的 loss 之和**：早停判断（连续 N 步 loss 不降则停）
- **最近 N 步的梯度范数之和**：梯度裁剪、爆炸检测
- **最近 N 步的 learning rate**：调度器决策依据
- **最近 N 个样本的特征均值**：数据分布漂移检测

### 3.2 朴素做法 vs BIT

**朴素做法**：用 list 存窗口，每次查区间和就遍历累加。

```python
window = []  # 最近 N 步的 loss
def window_sum():
    return sum(window)  # O(N)
```

每步训练都查一次窗口和，总开销 O(N × T)，T 是训练步数。N=10000, T=100000 时，10 亿次加法。

**BIT 做法**：用 BIT 维护窗口内 loss，更新和查询都是 O(log N)。

```python
bit = BIT(N)
def update_step(i, loss):
    bit.set(i, loss)        # O(log N)
def window_sum(l, r):
    return bit.range_sum(l, r)  # O(log N)
```

总开销 O(log N × T)。N=10000, T=100000 时，约 130 万次操作。**快 700x**。

### 3.3 demo 实测

n=4096，做 n 次更新 + n 次区间和查询：

| 实现 | 耗时 (ms) | 加速比 |
|------|-----------|--------|
| 朴素累加 O(n) | ~68 | 1.00x |
| BIT O(log n) | ~15 | **4.41x** |

n 更大时加速更明显。n=65536 时 BIT 可加速 10x+（O(n) vs O(log n) 的差距随 n 增长）。

### 3.4 窗口滑动的处理

流式数据中窗口是滑动的：新数据进窗口，老数据出窗口。BIT 处理滑动有两种方式：

**方式 1：环形复用槽位**（本 demo 做法）
- BIT 有 N 个槽位，对应窗口的 N 个位置
- 新数据写入槽位 `pos = (pos % N) + 1`，覆盖最老的
- 适合「只需窗口内总和」的场景

**方式 2：显式加减**
- 新数据进窗口：`bit.update(new_pos, new_value)`
- 老数据出窗口：`bit.update(old_pos, -old_value)`（减去老值）
- 适合「需要精确知道每个位置值」的场景

### 3.5 其他窗口统计需求

| 统计需求 | 数据结构 | 复杂度 |
|----------|----------|--------|
| 窗口内和 | BIT | O(log n) update/query |
| 窗口内最值 | 线段树 / 单调队列 | O(log n) / O(1) |
| 窗口内中位数 | 双堆 / 桶 | O(log n) |
| 窗口内分位数 | 顺序统计树 | O(log n) |
| 窗口内方差 | 两个 BIT（和 + 平方和） | O(log n) |

本 demo 只展示「窗口内和」（BIT），其他需求可类似扩展。

## 4. 去重的重要性

### 4.1 训练数据为什么会有重复？

- **爬虫重复抓取**：同一页面被多次抓取
- **数据增强重复**：增强操作可能产生与原数据相同的样本
- **多源合并**：多个数据集合并时有重叠
- **分布式训练同步**：多 worker 可能读到相同数据（sampler 配置不当）
- **人工标注重复**：同一样本被多次标注

### 4.2 重复样本的危害

- **污染统计**：loss 被重复样本拉低，高估模型性能
  - 假设 10% 样本重复，loss 会被低估约 10%，模型看似更好但实际泛化更差
- **浪费算力**：重复计算已知样本的梯度，GPU 算力浪费
- **导致过拟合**：模型对重复样本过拟合，记忆而非泛化
- **扭曲分布**：重复样本的类别/特征分布被放大，模型偏向这些样本

### 4.3 精确去重 vs 近似去重

**精确去重（set）**：
- 内存：O(n × key_size)，每个 key 一个哈希表条目 + 元素对象
- 速度：O(1) 平均（哈希表）
- 准确性：100% 精确，无误判
- 问题：百万/亿级 key 时内存压力大

**近似去重（布隆过滤器）**：
- 内存：O(m bits)，m = -n × ln(p) / (ln2)²，与 key_size 无关
- 速度：O(k) ≈ O(1)，k 个哈希 + 位数组操作
- 准确性：可能误判（假阳性），但误判率可控（如 1%）
- 优势：内存远小于 set，适合大规模流式去重

### 4.4 demo 实测

n=50000 个 int key：

| 维度 | set | 布隆 | 说明 |
|------|-----|------|------|
| 速度 | 7.3 ms | 288 ms | Python 中 set 是 C 优化，布隆是纯 Python 循环 |
| 内存 | 3,497,340 bytes | 59,907 bytes | **布隆是 set 的 1/58** |

速度上 Python 层布隆不占优（set 是 C 实现），但内存上布隆优势巨大（58x）。
在 C/C++/Rust 中布隆速度也很快（k 次哈希 + 位数组操作都是 O(1) 常数）。

### 4.5 布隆误判的影响

布隆误判（假阳性）的后果：把一个**新样本误判为重复**，从而丢弃它。
对训练的影响：

- 丢失少量新样本（误判率 1% → 丢 1% 的新样本）
- 训练数据本就有冗余（百万级样本中丢 1% 可忽略）
- 不会引入错误样本（假阳性只丢不增）

对比假阴性（漏判重复）：会把重复样本当新样本留下，污染训练。布隆**无假阴性**，
所以不会漏判重复——这是布隆用于去重的关键优势。

### 4.6 何时用布隆 vs set？

| 场景 | 推荐 | 原因 |
|------|------|------|
| 小规模（< 10万）| set | 内存不是问题，精确更好 |
| 大规模（百万+） | 布隆 | 内存优势显著，误判可接受 |
| 流式（持续流入） | 布隆 | set 持续增长，布隆固定大小 |
| 需要删除 | set / Counting Bloom | 基本布隆不支持删除 |
| 需要精确 | set | 布隆有误判 |

## 5. demo 结果解读

### 5.1 管道运行统计

```
输入样本总数      : 2000
去重丢弃（真重复）: 557
布隆误判（假阳性）: 0
背压丢帧          : 0
输出 batch 数     : 46
输出样本数        : 1443
窗口平均 loss     : 1.5371
```

- **输入 2000，去重 557**：dup_rate=0.15 注入了 15% 重复，实际去重 557/2000 ≈ 28%
  （因为重复 ID 的注入方式导致部分 ID 重复多次）
- **布隆误判 0**：2000 个样本的布隆（n=2000, p=0.01）误判率极低，实测 0 次
- **输出 1443 样本，46 个 batch**：1443 = 2000 - 557（去重后），46 = ceil(1443/32)
- **窗口平均 loss 1.5371**：loss 在 [0.1, 3.0] 均匀分布，期望 1.55，实测吻合

### 5.2 性能对比解读

**BIT vs 朴素（4.41x）**：
- BIT 的 O(log n) 在 n=4096 时约 12 步，朴素 O(n) 要 4096 步
- 加速比 4.41x 而非理论 341x（4096/12），因为 BIT 的常数更大（每次更新要跳多个节点）
- n 更大时加速更明显（n=65536 时 BIT 可加速 10x+）

**布隆 vs set（内存 58x）**：
- set 3.5MB vs 布隆 60KB，布隆内存省 58 倍
- 速度上布隆慢（Python 层循环 vs set 的 C 实现），在 C/C++ 中布隆速度也快
- 核心价值是内存，不是速度（在 Python 中）

**管道背压 vs 无界（内存 7500 vs 256）**：
- 无界 list 内存峰值 7500 items（上游快、下游慢，数据堆积）
- 有界队列内存峰值 256 items（满了丢老的，固定上限）
- 代价：有界队列丢帧 7244（丢的是老数据，对训练影响可控）

**RingBuffer vs list.pop(0)（20.31x）**：
- list.pop(0) 每次左移 8192 个元素，O(n) 开销
- RingBuffer 只改写指针，O(1) 操作
- 窗口越大，RingBuffer 优势越明显

### 5.3 协作的意义

四种数据结构各自解决一个子问题，协作完成流式数据管道：

```
队列  → 连接各阶段，背压控制内存
环形缓冲 → 保留最近 N 个，固定内存
BIT   → 窗口内 O(log n) 区间和
布隆   → O(1) 判重，内存远小于 set
```

单一数据结构无法完成：队列不能统计、BIT 不能去重、布隆不能组织管道。
协作让每种数据结构发挥其优势，共同支撑流式训练。

## 6. 生产级实现

### 6.1 PyTorch DataLoader

PyTorch 的 `DataLoader` 是数据管道的标准实现：

```python
from torch.utils.data import DataLoader, Dataset

class MyDataset(Dataset):
    def __len__(self): return 1_000_000
    def __getitem__(self, idx):
        # 读盘 → 解码 → 预处理（单样本）
        return load_sample(idx)

loader = DataLoader(
    MyDataset(),
    batch_size=32,
    num_workers=4,      # 4 个 worker 进程（多阶段管道）
    pin_memory=True,    # 锁页内存，加速 GPU 传输
    prefetch_factor=2,  # 每个 worker 预取 2 个 batch（有界队列）
    drop_last=True,     # 不足 batch_size 丢弃（背压）
)
```

内部机制：
- `num_workers=4`：4 个子进程并行加载数据（多阶段管道的并行）
- `prefetch_factor=2`：每个 worker 预取 2 个 batch，用有界队列连接（队列 + 背压）
- `pin_memory=True`：预分配锁页内存，加速 CPU → GPU 传输
- 主进程从 worker 的队列取 batch，喂给 GPU

### 6.2 WebDataset

WebDataset 用于流式加载大模型训练数据（TB 级）：

```python
import webdataset as wds

dataset = (
    wds.WebDataset("shards-{000000..000999}.tar")
    .shuffle(1000)       # 滑动窗口 shuffle（环形缓冲）
    .decode("torch")     # 解码
    .map(augment)        # 数据增强
    .batched(32)         # 组 batch
)
loader = torch.utils.data.DataLoader(dataset, num_workers=4)
```

特点：
- **流式**：tar shard 逐个读，不全装入内存（流式处理）
- **shuffle 窗口**：用环形缓冲做滑动窗口 shuffle（不能全局 shuffle，只能窗口内）
- **去重**：可用 key 去重（布隆或集合）
- **管道**：`.shuffle().decode().map().batched()` 链式管道

### 6.3 Kafka 流式管道

Kafka 用于分布式流式数据管道（如在线学习）：

```
数据源 → Kafka topic → 消费者（训练进程）→ 模型更新
```

- **队列**：Kafka topic 是分布式队列，分区 + 消费者组实现多阶段管道
- **窗口**：Kafka Streams 的窗口存储（基于 RocksDB）做滑动窗口统计
- **去重**：Kafka 的 exactly-once 语义 + 幂等生产者做消息去重
- **背压**：消费者按能力拉取，天然背压

### 6.4 TensorFlow tf.data

```python
dataset = (
    tf.data.Dataset.from_tensor_slices(file_paths)
    .interleave(load_and_decode, num_parallel_calls=4)  # 多阶段并行
    .map(augment, num_parallel_calls=4)                 # 增强并行
    .prefetch(64)                                        # 有界队列预取
    .batch(32)                                           # 组 batch
)
```

- `interleave`：多文件并行加载（多阶段管道）
- `prefetch(64)`：有界队列预取 64 个 batch（队列 + 背压）
- `shuffle(buffer_size=10000)`：滑动窗口 shuffle（环形缓冲）

### 6.5 HuggingFace Datasets

```python
from datasets import load_dataset

dataset = load_dataset("wikipedia", "20220301.en", streaming=True)
# streaming=True → 流式加载，不全装入内存

for sample in dataset:
    # 逐个样本处理（流式管道）
    ...
```

- `streaming=True`：流式加载，用迭代器逐个产出样本
- 不需要把整个数据集装入内存（TB 级数据集也能处理）
- 可与 `DataLoader` 结合做多阶段管道

## 7. 扩展：更多流式数据结构

### 7.1 滑动窗口的更多数据结构

| 需求 | 数据结构 | 复杂度 | 场景 |
|------|----------|--------|------|
| 窗口和 | BIT | O(log n) | loss/梯度监控 |
| 窗口最值 | 单调队列 | O(1) 均摊 | 梯度裁剪阈值 |
| 窗口中位数 | 双堆 | O(log n) | 鲁棒统计 |
| 窗口分位数 | 顺序统计树 | O(log n) | 分布监控 |
| 窗口 top-k | 容量受限堆 | O(log k) | 热门样本追踪 |

### 7.2 去重的更多数据结构

| 需求 | 数据结构 | 复杂度 | 场景 |
|------|----------|--------|------|
| 精确去重 | set / hash table | O(1) | 小规模 |
| 近似去重 | 布隆过滤器 | O(k) | 大规模、可容忍误判 |
| 近似去重 + 删除 | Counting Bloom / Cuckoo Filter | O(k) | 需要删除 |
| 基数估计 | HyperLogLog | O(1) | 统计唯一值数量 |
| 精确基数 | set | O(n) | 小规模 |

### 7.3 流式处理的更多模式

- **窗口聚合**：滑动窗口内做 sum/avg/max/min（BIT / 线段树 / 单调队列）
- **流式 join**：两个流按 key join（哈希表 + 窗口）
- **流式采样**：蓄水池采样（reservoir sampling），固定内存从流中均匀采样
- **流式分位数**：t-digest / GK 算法，固定内存估计流式分位数

## 8. 小结

AI 训练数据的流式处理需要四种数据结构协作：

| 子问题 | 数据结构 | 解决方案 |
|--------|----------|----------|
| 多阶段连接 | 队列 | 有界队列 + 背压，阶段间缓冲 |
| 窗口保留 | 环形缓冲 | 定长数组 + 写指针，O(1) 覆盖最老 |
| 窗口统计 | BIT | lowbit 分块，O(log n) 区间和 |
| 流式去重 | 布隆过滤器 | 多哈希 + 位数组，O(1) 判重 |

生产级实现（PyTorch DataLoader、WebDataset、Kafka、tf.data）都基于类似的数据结构协作。
理解这些数据结构的原理，才能更好地使用和调优生产级数据管道。
