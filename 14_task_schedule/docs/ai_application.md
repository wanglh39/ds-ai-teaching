# 任务调度与批处理的 AI 应用：LLM 推理服务调度

> 本文档讲清「任务调度与批处理在 AI 里干什么」。原理见 `principle.md`。核心：LLM 推理服务要把海量请求高效调度到有限 GPU 节点，需要 4 种数据结构协作——堆做优先级调度、DAG 管任务依赖、队列做动态批处理、一致性哈希做负载均衡。

## 1. LLM 推理服务的调度问题

### 1.1 从单机推理到推理服务

单个 LLM 推理很简单：给一个 prompt，模型返回结果。但当你要把 LLM 做成**服务**（像 OpenAI API 那样），问题就复杂了：

```
单机推理（一个人用）：
  prompt → model → result
  → 没有调度问题

推理服务（千万人用）：
  10000 req/s → ??? → GPU 集群 → results
  → 请求有优先级、有依赖、要批处理、要负载均衡
```

一个生产级 LLM 推理服务要处理：

- **高并发**：每秒几千到几万请求
- **异构请求**：VIP 用户、普通用户、后台批处理混在一起
- **有限资源**：GPU 贵且少，要榨干利用率
- **动态扩缩容**：流量高峰要加节点、低谷要减节点

这 4 个需求正好对应 4 种数据结构。

### 1.2 为什么调度是核心

LLM 推理的算力成本极高（一张 A100 GPU 数万美元，每小时运行成本数美元）。调度不好会导致：

- **GPU 空闲**：请求逐个处理，GPU 利用率 5-10% → 算力浪费 90%
- **SLA 违规**：VIP 用户请求被普通请求阻塞 → 付费客户流失
- **扩容低效**：加节点时大量请求迁移、KV cache 失效 → 扩容反而降低吞吐
- **流水线阻塞**：推理阶段乱序执行 → 死锁或重做

好的调度能让 GPU 利用率到 70-90%、VIP 延迟降 20x、扩容迁移量降 4x。这就是为什么 vLLM、Triton 这些框架把调度作为核心竞争力。

## 2. 优先级调度：VIP 用户与 SLA 保障

### 2.1 SLA（服务等级协议）

商业 LLM 服务通常对不同用户承诺不同的 SLA：

| 用户等级 | SLA 承诺 | 优先级 |
|---|---|---|
| 企业客户（VIP） | P99 延迟 < 500ms | 1（最高） |
| 个人付费用户 | P99 延迟 < 2s | 2 |
| 免费用户 | 尽力而为 | 3 |
| 后台批处理 | 无承诺 | 4（最低） |

### 2.2 FIFO 的灾难

如果用 FIFO 调度（先到先服务），当免费用户请求大量到达时，VIP 请求会被阻塞：

```
时刻 0-100：1000 个免费请求到达，入 FIFO 队列
时刻 101：1 个 VIP 请求到达，入 FIFO 队列（排在 1000 个免费请求后面）
时刻 1000+：VIP 请求才被处理 → 延迟 > 900 步 → SLA 违规
```

实测：200 个请求（20 VIP 后到），FIFO 让 VIP 平均执行位置 = 189.5（几乎最后）。

### 2.3 堆的解法

用最小堆，按 priority 排序。VIP 请求（priority=1）后到也能插队到堆顶：

```
时刻 0-100：1000 个免费请求入堆（priority=3）
时刻 101：1 个 VIP 请求入堆（priority=1）→ 堆顶变成 VIP
时刻 102：VIP 请求立即被 pop 处理 → 延迟 = 1 步 → SLA 满足
```

实测：同样 200 请求，优先级堆让 VIP 平均执行位置 = 9.5，比 FIFO 快 **19.9x**。

### 2.4 同优先级内 FIFO 的必要性

只按 priority 排序有个陷阱：同优先级请求可能乱序（堆不保证同 key 的插入顺序）。用 `(priority, seq)` 做比较 key，seq 是单调递增的插入序号，保证同优先级内先入先出。这避免了一个微妙问题：VIP 用户 A 先发请求、VIP 用户 B 后发，如果 B 先返回，A 会觉得不公平。

### 2.5 抢占式 vs 非抢占式

本 demo 是**非抢占式**：请求一旦开始处理就不中断。生产级系统有时用**抢占式**：VIP 请求到达时，正在处理的普通请求被暂停、GPU 让给 VIP。vLLM 的 priority preemption 就是这样：高优先级请求可以抢占低优先级的 KV cache。

## 3. 动态批处理：vLLM 的 continuous batching

### 3.1 为什么必须批处理

LLM 推理的 `prefill` 阶段（处理 prompt、生成 KV cache）是计算密集的。GPU 的算力通常远超单个请求的需要：

```
单请求 prefill：
  GPU 算力：100 TFLOPS
  单请求需要：1 TFLOPS
  → 利用率 1% → 99% 算力浪费

批处理 prefill（batch_size=8）：
  8 个请求一起 prefill
  → 利用率 8% → 仍然低，但 attention 矩阵乘法批量化后实际利用率 70-90%
```

批处理让多个请求共享一次 prefill 计算，GPU 利用率从 5% 提升到 70-90%，吞吐量提升 3-10 倍。

### 3.2 静态批处理的局限

最简单的批处理是**静态批处理**：攒够 batch_size 才发批。问题：

- **低流量尾延迟高**：流量低时，请求要等很久才攒够一批
- **长短请求拖累**：批内最长请求决定整批耗时，短请求被拖累
- **不能动态调整**：批一旦发出就不能加新请求

### 3.3 动态批处理：队列 + 超时

**动态批处理**用队列收集请求，两个触发条件：

- 凑够 batch_size → 立即发批
- 超时 max_wait → 强制发批（即使没凑够）

```
时刻 0：3 个请求入队，batch_size=8，没凑够，等
时刻 1：2 个请求入队，累计 5，没凑够，等
时刻 5：超时 max_wait=5，强制发批（5 个请求）
时刻 6：10 个请求突然入队，凑够 8，立即发批（8 个请求），剩 2 个等
```

实测：200 请求，batch_size=8，动态批处理吞吐量 = 0.33 req/ms，单请求 = 0.10 req/ms，**3.33x 提升**。

### 3.4 vLLM 的 continuous batching

**vLLM** 的 continuous batching（持续批处理）比上面更激进：

- **不等批完成才接新**：每个 decode step 都检查有没有新请求可以加入当前批
- **请求可中途退出**：批内某请求完成就退出，新请求立刻补位
- **PagedAttention 配合**：KV cache 分页管理，新请求加入批不需要连续内存

```
传统动态批处理：
  批 [r1, r2, r3, r4] → 全部完成 → 才接下一批
  → 批内最长请求拖累整批

vLLM continuous batching：
  step 1: 批 [r1, r2, r3, r4]
  step 2: r2 完成，r5 加入 → 批 [r1, r3, r4, r5]
  step 3: r1 完成，r6 加入 → 批 [r3, r4, r5, r6]
  → 批持续满载，没有"等整批完成"的空窗
```

本质还是队列 + 凑批，但"批"的边界是动态的、请求可以中途加入/退出。

### 3.5 Triton Inference Server 的动态批处理

NVIDIA **Triton** 的动态批处理更接近本 demo 的实现：

- 配置 `max_batch_size` 和 `preferred_batch_size`
- 请求入队列，满足 `preferred_batch_size` 或超时 `max_queue_delay` 发批
- 支持 multiple model instances（同一模型多个实例并行）

Triton 的 `dynamic_batcher` 配置就是本 demo 的 `batch_size` 和 `max_wait`。

## 4. 负载均衡与一致性哈希

### 4.1 多节点负载均衡

LLM 推理服务通常有多个 GPU 节点（worker）。请求要分发到节点，要求：

- **均衡**：每个节点分到差不多数量的请求（避免有的节点过载、有的空闲）
- **稳定**：节点增减时尽量少迁移请求（已有 KV cache 的请求迁移代价高）
- **可扩展**：加节点要简单（扩容），删节点要平滑（缩容/故障转移）

### 4.2 取模哈希的致命缺陷

最简单的负载均衡是**取模哈希**：`node = hash(key) % N`。

```
4 节点：hash(key) % 4 → node_0, node_1, node_2, node_3
加 1 节点（N=5）：hash(key) % 5 → 几乎所有 key 重新映射

实测：10000 key，4 节点 → 5 节点，8011 key 迁移（80%）
```

对 LLM 服务，迁移意味着：

- 已有 KV cache 失效（KV cache 可能占几 GB 显存）
- 请求要重新 prefill（昂贵计算）
- 用户感知到延迟突增

80% 的请求要重新 prefill，相当于扩容反而让服务性能暴跌。

### 4.3 一致性哈希的解法

**一致性哈希**把 hash 值域看成环，节点和 key 都映射到环上，key 归属沿环顺时针的第一个节点。

```
环（4 节点）：
         node_0
        /        \
   key_a          key_b
      |            |
   key_d          key_c
        \        /
         node_2

加 node_4（插在 key_a 和 node_0 之间）：
  → 只有 key_a 改归 node_4，其他 key 不变
  → 迁移量 ≈ k/n = 10000/4 = 2500
```

实测：10000 key，4 节点加 1 节点，一致性哈希迁移 1992 key（19.92%），取模哈希迁移 8011 key（80.11%），**一致性哈希迁移量是取模哈希的 1/4**。

### 4.4 虚拟节点：均匀分布

如果每个物理节点只对应环上 1 个点，节点少时分布会很不均匀。**虚拟节点**让每个物理节点对应环上 150 个虚拟点，10000 key 在 4 节点上的分布偏差 < 5%。

```
实测（10000 key，4 节点，150 虚拟节点）：
  node_0: 286 key
  node_1: 213 key
  node_2: 247 key
  node_3: 254 key
  均值 250，最大偏差 37（< 5%）
```

### 4.5 节点增减的实际场景

- **扩容**：流量高峰，加节点分担负载。一致性哈希只迁移 1/n 的请求，新节点立刻分担 1/n 流量，老节点负载下降。
- **缩容**：流量低谷，删节点省钱。被删节点的请求迁移到其他节点，每个节点只多接 1/(n-1) 的请求。
- **故障转移**：某节点宕机，等价于"删节点"。一致性哈希让故障影响最小化，只有故障节点上的请求需要迁移，其他节点不受影响。

### 4.6 与 KV cache 的协同

一致性哈希在 LLM 服务里特别重要，因为 **KV cache 是请求绑定的**：

- 请求 r 在 node_0 上推理，KV cache 存在 node_0 的显存里
- 如果 r 被迁移到 node_1，node_1 没有 r 的 KV cache，要重新 prefill
- 一致性哈希让节点增减时只有 1/n 的请求需要重新 prefill，其余请求的 KV cache 仍有效

这是为什么 vLLM、SGLang 等框架在多 worker 场景下用一致性哈希（或其变体）做请求路由。

## 5. demo 结果解读

### 5.1 优先级调度 vs FIFO

```
场景：200 请求，20 VIP 后到
优先级调度：VIP 平均执行位置 = 9.5
FIFO 调度  ：VIP 平均执行位置 = 189.5
→ FIFO 让 VIP 多等 19.9x
```

解读：VIP 请求后到，FIFO 把它们排到 180 个普通请求后面，平均要等 189.5 个位置才执行。优先级堆让 VIP 插队到堆顶，平均 9.5 个位置就执行。**堆让 SLA 保障成为可能**。

### 5.2 动态批处理 vs 单请求

```
场景：200 请求，batch_size=8
动态批处理：25 批，平均批大小 8.00，总耗时 600 ms，吞吐量 0.33 req/ms
单请求处理：总耗时 2000 ms，吞吐量 0.10 req/ms
→ 批处理吞吐量是单请求的 3.33x
```

解读：单请求每个独占 prefill（10ms），200 个 = 2000ms。批处理 8 个请求共享 prefill（10 + 2×7 = 24ms），25 批 = 600ms。**批处理让 GPU 利用率从 10% 提升到 70%+**。

### 5.3 一致性哈希 vs 取模哈希

```
场景：10000 key，4 节点，150 虚拟节点
加 1 节点：
  一致性哈希迁移 1992 key (19.92%)
  取模哈希迁移   8011 key (80.11%)
  → 取模哈希迁移量是一致性哈希的 4.0x
删 1 节点：
  一致性哈希迁移 2328 key
  取模哈希迁移   8019 key
```

解读：加节点时，取模哈希因为 N 从 4 变 5，几乎所有 key 的 `hash % N` 都变了，80% 要迁移。一致性哈希只在环上插入一个节点，只影响该节点附近一小段 key，迁移 20%。**一致性哈希让扩缩容的代价从 O(k) 降到 O(k/n)**。

### 5.4 完整推理服务模拟

```
配置：100 请求，batch_size=8，max_wait=5，4 节点
结果：16 批，平均批大小 6.25
  VIP 平均延迟 34.00 步，所有请求平均延迟 41.30 步
  批分发到 4 节点：1/4/6/5 批
```

解读：

- 16 批处理 100 请求，平均批大小 6.25（受 max_wait 超时影响，没每次都凑满 8）
- VIP 平均延迟 34 步 < 所有请求平均 41.3 步，**优先级调度生效**
- 4 节点分到 1/4/6/5 批，分布有偏差是因为批数少（16 批），key 多时偏差会更小

## 6. 生产级实现

### 6.1 vLLM

**vLLM**（UC Berkeley 开源）是当前最流行的 LLM 推理框架，核心创新：

- **PagedAttention**：KV cache 分页管理（类 OS 虚拟内存），解决 KV cache 内存碎片
- **Continuous Batching**：动态批处理 + 请求可中途加入/退出
- **Priority Scheduling**：支持请求优先级 + 抢占式调度
- **Multi-Worker**：多 GPU 节点用 Ray + 一致性哈希路由

对应本 demo：
- PagedAttention → 队列（DynamicBatcher）的底层优化
- Continuous Batching → 队列的更激进版本
- Priority Scheduling → 堆（PriorityHeap）
- Multi-Worker → 一致性哈希（ConsistentHashing）

### 6.2 Triton Inference Server

**Triton**（NVIDIA 出品）是生产级推理服务框架，核心特性：

- **Dynamic Batcher**：本 demo 的 DynamicBatcher 的工业级实现，配置 `max_batch_size` + `preferred_batch_size` + `max_queue_delay`
- **Multiple Model Instances**：同一模型多个实例并行，请求用轮询或一致性哈希分发
- **Model Ensembles**：DAG 流水线（模型链），如 ASR → LLM → TTS
- **Priority Queues**：支持请求优先级

对应本 demo：
- Dynamic Batcher → 队列（DynamicBatcher）
- Model Ensembles → DAG（DependencyDAG）
- Priority Queues → 堆（PriorityHeap）
- Multiple Instances → 一致性哈希（ConsistentHashing）

### 6.3 SGLang

**SGLang**（UC Berkeley 出品，vLLM 后续）更进一步：

- **RadixAttention**：用 Radix Tree 复用 KV cache（同前缀的请求共享 KV cache）
- **Structured Generation**：约束解码（JSON/正则约束输出）
- **Multi-Modal**：支持图像+文本输入

RadixAttention 用 Radix Tree（一种 Trie 变体）管理 KV cache 复用，本质是**用树结构表达 prompt 前缀的依赖关系**，和 DAG 拓扑排序的思想相通。

### 6.4 TensorRT-LLM

**TensorRT-LLM**（NVIDIA 出品）是 TensorRT 的 LLM 专用版：

- **In-flight Batching**：类 vLLM 的 continuous batching
- **Pipeline Parallelism**：流水线并行（不同层分配到不同 GPU），用 DAG 决定层间依赖
- **Tensor Parallelism**：张量并行（同一层的矩阵乘法切分到多 GPU）

Pipeline Parallelism 的层间依赖就是本 demo 的 DAG 拓扑排序：第 k 层依赖第 k-1 层的输出，拓扑排序给出合法的层执行顺序。

## 7. 调度策略的权衡

### 7.1 吞吐量 vs 延迟

- **批处理提高吞吐量**但**增加单请求延迟**（要等凑批）
- `max_wait` 是权衡旋钮：小 → 延迟低但批小（吞吐量低）；大 → 批大但延迟高
- VIP 请求可以绕过批处理直接执行（牺牲吞吐量保延迟）

### 7.2 公平 vs 优先级

- **FIFO 公平**但**无优先级**（VIP 被阻塞）
- **优先级堆**保障 VIP 但**可能饿死低优先级**（后台请求永远排不上）
- 解法：老化（aging）——等待时间长的低优先级请求自动升优先级

### 7.3 均衡 vs 稳定

- **取模哈希均衡**但**节点增减不稳定**（80% 迁移）
- **一致性哈希稳定**但**查归属稍慢**（O(log n) vs O(1)）
- 对 LLM 服务，稳定更重要（KV cache 迁移代价 >> 查归属开销）

## 8. 监控指标

生产级推理服务要监控的关键指标：

| 指标 | 含义 | 对应数据结构 |
|---|---|---|
| QPS | 每秒请求数 | 队列（批处理吞吐） |
| P50/P99 延迟 | 请求延迟分位数 | 堆（优先级保障 P99） |
| GPU 利用率 | GPU 算力使用比例 | 队列（批处理提升利用率） |
| 批大小分布 | 每批的请求数分布 | 队列（DynamicBatcher） |
| 节点负载方差 | 各节点请求数的方差 | 一致性哈希（分布均衡度） |
| 迁移率 | 节点增减时 key 迁移比例 | 一致性哈希（O(k/n)） |

## 9. 总结

LLM 推理服务调度是 4 种数据结构的协奏：

- **堆** → 优先级调度（VIP/SLA 保障，19.9x 延迟优势）
- **DAG** → 任务依赖（推理流水线拓扑排序，消除死锁/重做）
- **队列** → 动态批处理（凑批提高吞吐量，3.33x 吞吐优势）
- **一致性哈希** → 负载均衡（节点增减最少迁移，4x 迁移优势）

生产级系统 vLLM、Triton、SGLang、TensorRT-LLM 底层都是这 4 种数据结构的不同实现与组合。理解了这 4 种数据结构的协作，就抓住了 LLM 推理服务调度的本质。
