    第 14 章 · 任务调度与批处理（扩展专题）¶

    AI 场景：LLM 推理服务的任务调度、动态批处理、负载均衡 数据结构：堆 + DAG + 队列 + 一致性哈希（4 种协作）

    本章要回答的问题¶

    • 请求有优先级，谁先处理？（堆）
    • 推理流水线有依赖，按什么顺序执行？（DAG + 拓扑排序）
    • 请求要凑批提高吞吐量，怎么收集？（队列 + 动态批处理）
    • 多节点负载均衡，节点增减怎么少迁移？（一致性哈希）
    • 4 种数据结构如何协奏？

    扩展专题定位¶

    前 12 章是「一个数据结构 → 一个 AI 优化」。第 13 章起是扩展专题：一个 AI 应用场景 → 多种数据结构协作。本章展示堆、DAG、队列、一致性哈希如何协作解决 LLM 推理服务的调度问题。

    原理¶

    任务调度与批处理的数据结构原理：堆 + DAG + 队列 + 一致性哈希¶

    本文档讲清「LLM 推理服务调度为什么需要 4 种数据结构协作」。AI 应用（vLLM/Triton Inference Server 推理服务调度）见 ai_application.md。前 12 章是「一个数据结构 → 一个 AI 优化」，本章是扩展专题：一个 AI 应用场景 → 多种数据结构协作。

    0. 为什么是 4 种数据结构¶

    LLM 推理服务（Inference Serving）的核心问题是：如何把海量推理请求高效调度到有限 GPU 节点上。这一个问题分解出 4 个子问题，每个子问题对应一种数据结构：

    子问题 数据结构 作用
    请求有优先级，谁先处理？ 堆 优先级调度（VIP/SLA 保障）
    任务有依赖，按什么顺序执行？ DAG + 拓扑排序 流水线合法执行顺序
    请求要凑批，怎么收集？ 队列 动态批处理（continuous batching）
    多节点负载均衡，节点增减怎么少迁移？ 一致性哈希 环形空间 + 虚拟节点

    这 4 种数据结构不是独立工作，而是协奏：请求到达 → 堆按优先级排序 → DAG 检查依赖决定就绪 → 队列收集凑批 → 一致性哈希把批分发到节点。

    1. 堆与优先级调度¶

    1.1 为什么不能用 FIFO¶

    LLM 推理服务面对的请求不是平等的：

    • VIP 用户（付费企业客户）：SLA 要求 P99 延迟 < 500ms
    • 普通用户：尽力而为，延迟 1-2s 可接受
    • 后台批处理（离线生成、数据标注）：延迟无要求，趁空闲跑

    如果用 FIFO 队列调度，先到的先处理。当大量普通请求先到达、VIP 请求后到达时，VIP 请求会排在普通请求后面，违反 SLA。

    FIFO 队列（VIP 后到，被阻塞）：
  [user_0] [user_1] [user_2] ... [user_199] [vip_0] [vip_1]
  → VIP 平均执行位置 = 189.5（几乎最后才处理）

优先级堆（VIP 插队）：
  [vip_0] [vip_1] [user_0] [user_1] ... [user_199]
  → VIP 平均执行位置 = 9.5（立刻处理）

    1.2 堆：O(log n) 的优先级队列¶

    堆（Heap）是一棵完全二叉树，满足堆序性质：每个节点的值 ≤ 子节点的值（最小堆）。堆的核心操作：

    • push(x)：插入元素，O(log n)（上浮调整）
    • pop()：取出堆顶（最小元），O(log n)（下沉调整）
    • peek()：看堆顶，O(1)

    用堆做优先级调度，每个请求带一个 priority 字段（1=VIP, 2=普通, 3=后台），堆顶永远是优先级最高（priority 值最小）的请求。

    @dataclass(order=True)
class Request:
    priority: int       # 1=VIP, 2=普通, 3=后台（先比较）
    seq: int            # 同优先级内 FIFO 的插入序号（再比较）
    user: str = field(compare=False)
    prompt: str = field(compare=False)

    @dataclass(order=True) 让 Request 可比较：先比 priority，同 priority 比 seq（保证同优先级内 FIFO，不会饿死早期请求）。heapq 自动用这个顺序维护最小堆。

    1.3 同优先级内 FIFO 的关键¶

    只按 priority 排序有个问题：同优先级的请求可能乱序。比如两个普通请求 user_0 先到、user_1 后到，如果只比 priority，pop 顺序可能颠倒。加一个单调递增的 seq 字段做次序比较，保证同优先级内先入先出。这是优先级队列的标准技巧。

    1.4 复杂度对比¶

    操作 FIFO 队列 堆
    push O(1) O(log n)
    pop O(1) O(log n)
    优先级保障 无 有

    堆的 push/pop 比 FIFO 多一个 log n 因子，但换来优先级保障。对 LLM 服务，n 通常是几百到几千（队列里的请求），log n ≈ 10，开销可忽略，而 SLA 保障的价值巨大。

    2. DAG 与任务依赖¶

    2.1 LLM 推理流水线是 DAG¶

    一个 LLM 推理请求不是一步完成的，而是一条流水线：

    tokenize → embed → prefill → decode → detokenize → postprocess
  分词     嵌入    预填充    解码      反分词       后处理

    每一步依赖前一步的输出。更复杂的场景还有分支：

                        ┌→ safety_check ┐
tokenize → embed → │                ├→ decode → detokenize
                    └→ cache_lookup ┘

    把每个阶段看成顶点，依赖关系看成有向边，整个流水线是一个 DAG（有向无环图）。

    2.2 为什么必须是 DAG¶

    流水线必须是无环的，因为：

    • 如果有环 A → B → A，A 等 B 完成、B 等 A 完成 → 死锁
    • DAG 保证至少有一个无前置的阶段（源点），可以从源点开始
    • DAG 的拓扑排序给出合法的全局执行顺序：每个阶段的所有前置都在它之前

    2.3 拓扑排序：Kahn 算法¶

    Kahn 算法（BFS 拓扑排序）：

    1. 计算每个顶点的入度（前置数）
    2. 入度为 0 的顶点入队（无前置，可立即执行）
    3. 取队首 u，加入结果；对 u 的每个后继 v，v 的入度 -1；若 v 入度变 0，v 入队
    4. 重复直到队空
    tokenize → embed → prefill → decode → detokenize → postprocess

入度：tokenize=0, embed=1, prefill=1, decode=1, detokenize=1, postprocess=1

第 1 轮：tokenize 入度 0，出队 → embed 入度变 0
第 2 轮：embed 出队 → prefill 入度变 0
... 最终顺序 = [tokenize, embed, prefill, decode, detokenize, postprocess]

    复杂度 O(V + E)：每个顶点入队/出队一次，每条边在删边时检查一次。

    2.4 拓扑层级：可并行的分组¶

    topological_levels() 把 DAG 按"层"分组：

    • 层 0 = 无前置的阶段（可立即开始）
    • 层 k = 所有前置都在 0..k-1 层的阶段

    同层阶段无依赖关系，可以并行执行。这对 GPU 流水线并行（Pipeline Parallelism）很重要：不同层分配到不同 GPU，同层的分支（如 safety_check 和 cache_lookup）在同一 GPU 上并行。

    3. 队列与动态批处理¶

    3.1 为什么要批处理¶

    LLM 推理的 prefill 阶段（处理 prompt、填充 KV cache）是计算密集的。如果逐请求处理：

    • 每个请求独占一次 prefill，GPU 算力大量浪费在低 batch_size 上
    • GPU 利用率可能只有 5-10%

    如果把多个请求凑成一批一起 prefill：

    • 批内请求共享一次 prefill 计算（attention 矩阵乘法批量化）
    • GPU 利用率可提升到 70-90%
    • 吞吐量提升 3-10 倍（延迟略增，但 amortized 后单请求延迟反而可能降低）

    3.2 静态批处理的问题¶

    最简单的批处理是静态批处理：攒够 batch_size 个请求才发批。问题：

    • 低流量时，请求要等很久才攒够一批 → 尾延迟高
    • 请求长度不一时，批内最长的请求决定整批耗时 → 短请求被拖累

    3.3 动态批处理：队列 + 超时¶

    动态批处理（Dynamic Batching）用队列收集请求，满足任一条件就发批：

    • (a) 凑够：队列里请求数 ≥ batch_size → 立即发批
    • (b) 超时：距上一个批的等待时间 ≥ max_wait → 强制发批（即使没凑够）
    class DynamicBatcher:
    def __init__(self, batch_size=8, max_wait=5):
        self._queue: deque[Request] = deque()
        self._batch_size = batch_size
        self._max_wait = max_wait

    def try_flush(self, clock) -> Batch | None:
        if not self._queue:
            return None
        size_ok = len(self._queue) >= self._batch_size
        wait_ok = (clock - self._last_flush_clock) >= self._max_wait
        if not (size_ok or wait_ok):
            return None
        # 取出前 batch_size 个请求发批
        ...

    队列的 FIFO 保证：先到的请求先入批，不会饿死早期请求。max_wait 保证：低流量时请求不会无限等待。

    3.4 vLLM 的 continuous batching¶

    vLLM 的 continuous batching（持续批处理）比这更激进：

    • 不等批内所有请求完成才接新请求
    • 每个 decode step 都检查有没有新请求可以加入当前批
    • 配合 PagedAttention（分页 KV cache），批内请求可以动态加入/退出

    本质还是队列 + 凑批，只是"批"的边界是动态的、请求可以中途加入。

    3.5 吞吐量对比¶

    假设单请求 prefill 耗时 10ms，批大小 b 时耗时 10 + 2*(b-1) ms（amortized）：

    策略 200 请求总耗时 吞吐量
    单请求 200 × 10 = 2000 ms 0.10 req/ms
    动态批处理（batch_size=8） 25 批 × 24 ms = 600 ms 0.33 req/ms

    批处理吞吐量是单请求的 3.33x。

    4. 一致性哈希：环形空间 + 虚拟节点¶

    4.1 负载均衡问题¶

    LLM 推理服务通常有多个 GPU 节点。请求要分发到节点，要求：

    • 均衡：每个节点分到差不多数量的请求
    • 稳定：节点增减时，尽量少迁移请求（已有 KV cache 的请求迁移代价高）

    4.2 取模哈希：简单但迁移量大¶

    最简单的方案是取模哈希：node = hash(key) % N。

    • 优点：简单，分布均匀
    • 致命缺点：节点数 N 变化时，几乎所有 key 都要重映射
    N=4:  hash(key) % 4  →  node_0, node_1, node_2, node_3
N=5:  hash(key) % 5  →  node_0, node_1, node_2, node_3, node_4

加一个节点后，10000 个 key 里约 8011 个要迁移（80%）！

    对 LLM 服务，迁移意味着已有 KV cache 失效、请求要重新 prefill，代价巨大。

    4.3 一致性哈希：环形空间¶

    一致性哈希（Consistent Hashing）把 hash 值域看成环：

    1. 把 hash 值域 [0, 2^64) 看成一个环（首尾相连）
    2. 每个节点用 hash(node_name) 映射到环上一点
    3. 每个 key 用 hash(key) 映射到环上一点
    4. key 归属：沿环顺时针找到的第一个节点
    环（N=4，节点均匀分布）：

         node_0
        /        \
   key_a          key_b
      |            |
   key_d          key_c
        \        /
         node_2

  key_a → node_0（顺时针第一个）
  key_b → node_2（顺时针第一个，绕过 node_0 到 node_2）

    4.4 为什么节点增减只影响一小段 key¶

    加一个节点 node_4，只在环上 node_4 的位置插入一个点。只有原本顺时针走到 node_4 后面那个节点的 key 会改归 node_4，其他 key 不受影响。

    加 node_4 前：key_a → node_0
加 node_4 后（node_4 插在 key_a 和 node_0 之间）：
  key_a → node_4（顺时针第一个变成 node_4）
  其他 key 不变

迁移量 ≈ key 总数 / 节点数 = O(k/n)

    对比取模哈希的 O(k) 迁移，一致性哈希的 O(k/n) 迁移在 n=4 时只有 1/4 的 key 迁移，n=100 时只有 1%。

    4.5 虚拟节点：解决分布不均¶

    如果每个物理节点只对应环上 1 个点，节点少时分布会很不均匀（有的节点管一大段环、有的管一小段）。

    虚拟节点（Virtual Node）解决：每个物理节点对应环上 virtual_nodes 个虚拟节点（通常 150 个）。

    def add_node(self, node: str) -> None:
    for i in range(self._virtual_nodes):       # 150 个虚拟节点
        h = self._hash(f"{node}#{i}")          # node_0#0, node_0#1, ...
        self._ring_to_node[h] = node           # 虚拟点 → 物理节点
        bisect.insort(self._ring, h)           # 环上插入

    key 找到环上的虚拟点后，映射回物理节点。150 个虚拟点让 4 个物理节点在环上均匀分布，10000 个 key 的分布偏差 < 5%。

    4.6 迁移量对比（实测）¶

    场景 一致性哈希迁移 取模哈希迁移
    4 节点 → 加 1 节点 1992 / 10000 (19.92%) 8011 / 10000 (80.11%)
    5 节点 → 删 1 节点 2328 / 10000 8019 / 10000

    取模哈希加节点时迁移量是一致性哈希的 4.0x。节点越多，差距越大（一致性哈希 O(k/n) 随 n 增大更优）。

    4.7 复杂度对比¶

    操作 取模哈希 一致性哈希
    查 key 归属 O(1) O(log n)（二分找环上点）
    加/删节点 O(k) 重映射 O(k/n) 重映射
    加节点本身 O(1) O(virtual_nodes · log n)

    一致性哈希查归属稍慢（log n，但 n 是虚拟节点数，log(600) ≈ 10），换来节点增减时的最小迁移。对 LLM 服务，节点增减是运维常态（扩容、缩容、故障转移），最小迁移的价值远大于查归属的微小开销。

    5. 四种数据结构如何协作¶

    5.1 完整推理服务流程¶

    一个 LLM 推理请求从到达到完成，4 种数据结构协作的完整流程：

    请求到达
  │
  ▼
[1] 入优先级堆（堆）
  │  VIP 优先级 1，普通 2，后台 3
  │  堆顶 = 当前最高优先级请求
  ▼
[2] 检查依赖（DAG）
  │  请求要过流水线：tokenize → embed → prefill → ...
  │  DAG 拓扑排序给出合法执行顺序
  │  同层阶段可并行
  ▼
[3] 进入批处理器（队列）
  │  请求入队列，等待凑批
  │  凑够 batch_size 或超时 max_wait → 发批
  ▼
[4] 分发到节点（一致性哈希）
  │  批 id 用一致性哈希映射到节点
  │  节点增减时只有 O(k/n) 批迁移
  ▼
节点执行推理，返回结果

    5.2 各数据结构的职责边界¶

    数据结构 职责 不做什么
    堆 选下一个处理的请求（优先级） 不决定批大小、不决定节点
    DAG 决定阶段执行顺序（依赖） 不决定请求优先级、不决定批
    队列 收集请求凑批（批处理） 不决定优先级、不决定节点
    一致性哈希 选执行节点（负载均衡） 不决定优先级、不决定批

    4 种数据结构各司其职，通过明确的接口协作：

    • 堆 pop 出的请求 → 交给 DAG 检查依赖
    • DAG 就绪的请求 → 入队列凑批
    • 队列形成的批 → 用一致性哈希分发到节点

    5.3 为什么不能合并成一种¶

    有人可能问：能不能用一种数据结构搞定所有事？不能，因为 4 个子问题的需求正交：

    • 优先级需要偏序（VIP > 普通），堆最合适
    • 依赖需要图结构（DAG），队列/堆表达不了依赖
    • 凑批需要时间窗口（攒一段时间），堆/DAG 没有时间语义
    • 负载均衡需要均匀映射 + 最小迁移，堆/DAG/队列都做不到

    每种数据结构解决一个正交维度的问题，组合起来才完整覆盖推理服务调度的需求。这也是为什么生产级系统（vLLM、Triton）都同时用了这 4 种数据结构的不同变体。

    6. 复杂度汇总¶

    数据结构 核心操作 复杂度
    堆 push / pop O(log n)
    DAG 拓扑排序 O(V + E)
    队列 push / pop O(1)
    一致性哈希 查 key 归属 O(log n)（二分）
    一致性哈希 加/删节点 O(virtual_nodes · log n)
    一致性哈希 节点增减时 key 迁移 O(k/n)
    取模哈希 查 key 归属 O(1)
    取模哈希 节点增减时 key 迁移 O(k)

    7. 设计哲学¶

    7.1 分而治之¶

    推理服务调度看似一个复杂问题，分解成 4 个正交子问题后，每个子问题都有成熟的数据结构解法。这是分而治之（Divide and Conquer）在系统设计里的体现：不要造一个巨大的调度器，而是用几个各司其职的小组件协作。

    7.2 各取所长¶

    每种数据结构有自己的长处和短处：

    • 堆：优先级强，但不保持插入顺序（靠 seq 补）
    • DAG：表达依赖强，但不能动态加边（要保证无环）
    • 队列：简单公平，但无优先级
    • 一致性哈希：迁移少，但查归属稍慢

    组合起来，每种数据结构的长处正好覆盖一个子问题，短处被其他数据结构补上。

    7.3 生产级系统的同一本质¶

    vLLM、Triton Inference Server、SGLang、TensorRT-LLM 这些生产级推理框架，底层调度逻辑各不相同，但拆开看都是这 4 种数据结构的不同实现：

    • vLLM：堆（优先级）+ 队列（continuous batching）+ 一致性哈希（多 worker）
    • Triton：队列（动态批处理）+ 轮询（多模型实例）
    • SGLang：DAG（RadixAttention 复用 KV cache）+ 队列（批处理）

    理解了这 4 种数据结构的协作，就抓住了推理服务调度的本质。

    AI 应用¶

    任务调度与批处理的 AI 应用：LLM 推理服务调度¶

    本文档讲清「任务调度与批处理在 AI 里干什么」。原理见 principle.md。核心：LLM 推理服务要把海量请求高效调度到有限 GPU 节点，需要 4 种数据结构协作——堆做优先级调度、DAG 管任务依赖、队列做动态批处理、一致性哈希做负载均衡。

    1. LLM 推理服务的调度问题¶

    1.1 从单机推理到推理服务¶

    单个 LLM 推理很简单：给一个 prompt，模型返回结果。但当你要把 LLM 做成服务（像 OpenAI API 那样），问题就复杂了：

    单机推理（一个人用）：
  prompt → model → result
  → 没有调度问题

推理服务（千万人用）：
  10000 req/s → ??? → GPU 集群 → results
  → 请求有优先级、有依赖、要批处理、要负载均衡

    一个生产级 LLM 推理服务要处理：

    • 高并发：每秒几千到几万请求
    • 异构请求：VIP 用户、普通用户、后台批处理混在一起
    • 有限资源：GPU 贵且少，要榨干利用率
    • 动态扩缩容：流量高峰要加节点、低谷要减节点

    这 4 个需求正好对应 4 种数据结构。

    1.2 为什么调度是核心¶

    LLM 推理的算力成本极高（一张 A100 GPU 数万美元，每小时运行成本数美元）。调度不好会导致：

    • GPU 空闲：请求逐个处理，GPU 利用率 5-10% → 算力浪费 90%
    • SLA 违规：VIP 用户请求被普通请求阻塞 → 付费客户流失
    • 扩容低效：加节点时大量请求迁移、KV cache 失效 → 扩容反而降低吞吐
    • 流水线阻塞：推理阶段乱序执行 → 死锁或重做

    好的调度能让 GPU 利用率到 70-90%、VIP 延迟降 20x、扩容迁移量降 4x。这就是为什么 vLLM、Triton 这些框架把调度作为核心竞争力。

    2. 优先级调度：VIP 用户与 SLA 保障¶

    2.1 SLA（服务等级协议）¶

    商业 LLM 服务通常对不同用户承诺不同的 SLA：

    用户等级 SLA 承诺 优先级
    企业客户（VIP） P99 延迟 < 500ms 1（最高）
    个人付费用户 P99 延迟 < 2s 2
    免费用户 尽力而为 3
    后台批处理 无承诺 4（最低）

    2.2 FIFO 的灾难¶

    如果用 FIFO 调度（先到先服务），当免费用户请求大量到达时，VIP 请求会被阻塞：

    时刻 0-100：1000 个免费请求到达，入 FIFO 队列
时刻 101：1 个 VIP 请求到达，入 FIFO 队列（排在 1000 个免费请求后面）
时刻 1000+：VIP 请求才被处理 → 延迟 > 900 步 → SLA 违规

    实测：200 个请求（20 VIP 后到），FIFO 让 VIP 平均执行位置 = 189.5（几乎最后）。

    2.3 堆的解法¶

    用最小堆，按 priority 排序。VIP 请求（priority=1）后到也能插队到堆顶：

    时刻 0-100：1000 个免费请求入堆（priority=3）
时刻 101：1 个 VIP 请求入堆（priority=1）→ 堆顶变成 VIP
时刻 102：VIP 请求立即被 pop 处理 → 延迟 = 1 步 → SLA 满足

    实测：同样 200 请求，优先级堆让 VIP 平均执行位置 = 9.5，比 FIFO 快 19.9x。

    2.4 同优先级内 FIFO 的必要性¶

    只按 priority 排序有个陷阱：同优先级请求可能乱序（堆不保证同 key 的插入顺序）。用 (priority, seq) 做比较 key，seq 是单调递增的插入序号，保证同优先级内先入先出。这避免了一个微妙问题：VIP 用户 A 先发请求、VIP 用户 B 后发，如果 B 先返回，A 会觉得不公平。

    2.5 抢占式 vs 非抢占式¶

    本 demo 是非抢占式：请求一旦开始处理就不中断。生产级系统有时用抢占式：VIP 请求到达时，正在处理的普通请求被暂停、GPU 让给 VIP。vLLM 的 priority preemption 就是这样：高优先级请求可以抢占低优先级的 KV cache。

    3. 动态批处理：vLLM 的 continuous batching¶

    3.1 为什么必须批处理¶

    LLM 推理的 prefill 阶段（处理 prompt、生成 KV cache）是计算密集的。GPU 的算力通常远超单个请求的需要：

    单请求 prefill：
  GPU 算力：100 TFLOPS
  单请求需要：1 TFLOPS
  → 利用率 1% → 99% 算力浪费

批处理 prefill（batch_size=8）：
  8 个请求一起 prefill
  → 利用率 8% → 仍然低，但 attention 矩阵乘法批量化后实际利用率 70-90%

    批处理让多个请求共享一次 prefill 计算，GPU 利用率从 5% 提升到 70-90%，吞吐量提升 3-10 倍。

    3.2 静态批处理的局限¶

    最简单的批处理是静态批处理：攒够 batch_size 才发批。问题：

    • 低流量尾延迟高：流量低时，请求要等很久才攒够一批
    • 长短请求拖累：批内最长请求决定整批耗时，短请求被拖累
    • 不能动态调整：批一旦发出就不能加新请求

    3.3 动态批处理：队列 + 超时¶

    动态批处理用队列收集请求，两个触发条件：

    • 凑够 batch_size → 立即发批
    • 超时 max_wait → 强制发批（即使没凑够）
    时刻 0：3 个请求入队，batch_size=8，没凑够，等
时刻 1：2 个请求入队，累计 5，没凑够，等
时刻 5：超时 max_wait=5，强制发批（5 个请求）
时刻 6：10 个请求突然入队，凑够 8，立即发批（8 个请求），剩 2 个等

    实测：200 请求，batch_size=8，动态批处理吞吐量 = 0.33 req/ms，单请求 = 0.10 req/ms，3.33x 提升。

    3.4 vLLM 的 continuous batching¶

    vLLM 的 continuous batching（持续批处理）比上面更激进：

    • 不等批完成才接新：每个 decode step 都检查有没有新请求可以加入当前批
    • 请求可中途退出：批内某请求完成就退出，新请求立刻补位
    • PagedAttention 配合：KV cache 分页管理，新请求加入批不需要连续内存
    传统动态批处理：
  批 [r1, r2, r3, r4] → 全部完成 → 才接下一批
  → 批内最长请求拖累整批

vLLM continuous batching：
  step 1: 批 [r1, r2, r3, r4]
  step 2: r2 完成，r5 加入 → 批 [r1, r3, r4, r5]
  step 3: r1 完成，r6 加入 → 批 [r3, r4, r5, r6]
  → 批持续满载，没有"等整批完成"的空窗

    本质还是队列 + 凑批，但"批"的边界是动态的、请求可以中途加入/退出。

    3.5 Triton Inference Server 的动态批处理¶

    NVIDIA Triton 的动态批处理更接近本 demo 的实现：

    • 配置 max_batch_size 和 preferred_batch_size
    • 请求入队列，满足 preferred_batch_size 或超时 max_queue_delay 发批
    • 支持 multiple model instances（同一模型多个实例并行）

    Triton 的 dynamic_batcher 配置就是本 demo 的 batch_size 和 max_wait。

    4. 负载均衡与一致性哈希¶

    4.1 多节点负载均衡¶

    LLM 推理服务通常有多个 GPU 节点（worker）。请求要分发到节点，要求：

    • 均衡：每个节点分到差不多数量的请求（避免有的节点过载、有的空闲）
    • 稳定：节点增减时尽量少迁移请求（已有 KV cache 的请求迁移代价高）
    • 可扩展：加节点要简单（扩容），删节点要平滑（缩容/故障转移）

    4.2 取模哈希的致命缺陷¶

    最简单的负载均衡是取模哈希：node = hash(key) % N。

    4 节点：hash(key) % 4 → node_0, node_1, node_2, node_3
加 1 节点（N=5）：hash(key) % 5 → 几乎所有 key 重新映射

实测：10000 key，4 节点 → 5 节点，8011 key 迁移（80%）

    对 LLM 服务，迁移意味着：

    • 已有 KV cache 失效（KV cache 可能占几 GB 显存）
    • 请求要重新 prefill（昂贵计算）
    • 用户感知到延迟突增

    80% 的请求要重新 prefill，相当于扩容反而让服务性能暴跌。

    4.3 一致性哈希的解法¶

    一致性哈希把 hash 值域看成环，节点和 key 都映射到环上，key 归属沿环顺时针的第一个节点。

    环（4 节点）：
         node_0
        /        \
   key_a          key_b
      |            |
   key_d          key_c
        \        /
         node_2

加 node_4（插在 key_a 和 node_0 之间）：
  → 只有 key_a 改归 node_4，其他 key 不变
  → 迁移量 ≈ k/n = 10000/4 = 2500

    实测：10000 key，4 节点加 1 节点，一致性哈希迁移 1992 key（19.92%），取模哈希迁移 8011 key（80.11%），一致性哈希迁移量是取模哈希的 1/4。

    4.4 虚拟节点：均匀分布¶

    如果每个物理节点只对应环上 1 个点，节点少时分布会很不均匀。虚拟节点让每个物理节点对应环上 150 个虚拟点，10000 key 在 4 节点上的分布偏差 < 5%。

    实测（10000 key，4 节点，150 虚拟节点）：
  node_0: 286 key
  node_1: 213 key
  node_2: 247 key
  node_3: 254 key
  均值 250，最大偏差 37（< 5%）

    4.5 节点增减的实际场景¶

    • 扩容：流量高峰，加节点分担负载。一致性哈希只迁移 1/n 的请求，新节点立刻分担 1/n 流量，老节点负载下降。
    • 缩容：流量低谷，删节点省钱。被删节点的请求迁移到其他节点，每个节点只多接 1/(n-1) 的请求。
    • 故障转移：某节点宕机，等价于"删节点"。一致性哈希让故障影响最小化，只有故障节点上的请求需要迁移，其他节点不受影响。

    4.6 与 KV cache 的协同¶

    一致性哈希在 LLM 服务里特别重要，因为 KV cache 是请求绑定的：

    • 请求 r 在 node_0 上推理，KV cache 存在 node_0 的显存里
    • 如果 r 被迁移到 node_1，node_1 没有 r 的 KV cache，要重新 prefill
    • 一致性哈希让节点增减时只有 1/n 的请求需要重新 prefill，其余请求的 KV cache 仍有效

    这是为什么 vLLM、SGLang 等框架在多 worker 场景下用一致性哈希（或其变体）做请求路由。

    5. demo 结果解读¶

    5.1 优先级调度 vs FIFO¶

    场景：200 请求，20 VIP 后到
优先级调度：VIP 平均执行位置 = 9.5
FIFO 调度  ：VIP 平均执行位置 = 189.5
→ FIFO 让 VIP 多等 19.9x

    解读：VIP 请求后到，FIFO 把它们排到 180 个普通请求后面，平均要等 189.5 个位置才执行。优先级堆让 VIP 插队到堆顶，平均 9.5 个位置就执行。堆让 SLA 保障成为可能。

    5.2 动态批处理 vs 单请求¶

    场景：200 请求，batch_size=8
动态批处理：25 批，平均批大小 8.00，总耗时 600 ms，吞吐量 0.33 req/ms
单请求处理：总耗时 2000 ms，吞吐量 0.10 req/ms
→ 批处理吞吐量是单请求的 3.33x

    解读：单请求每个独占 prefill（10ms），200 个 = 2000ms。批处理 8 个请求共享 prefill（10 + 2×7 = 24ms），25 批 = 600ms。批处理让 GPU 利用率从 10% 提升到 70%+。

    5.3 一致性哈希 vs 取模哈希¶

    场景：10000 key，4 节点，150 虚拟节点
加 1 节点：
  一致性哈希迁移 1992 key (19.92%)
  取模哈希迁移   8011 key (80.11%)
  → 取模哈希迁移量是一致性哈希的 4.0x
删 1 节点：
  一致性哈希迁移 2328 key
  取模哈希迁移   8019 key

    解读：加节点时，取模哈希因为 N 从 4 变 5，几乎所有 key 的 hash % N 都变了，80% 要迁移。一致性哈希只在环上插入一个节点，只影响该节点附近一小段 key，迁移 20%。一致性哈希让扩缩容的代价从 O(k) 降到 O(k/n)。

    5.4 完整推理服务模拟¶

    配置：100 请求，batch_size=8，max_wait=5，4 节点
结果：16 批，平均批大小 6.25
  VIP 平均延迟 34.00 步，所有请求平均延迟 41.30 步
  批分发到 4 节点：1/4/6/5 批

    解读：

    • 16 批处理 100 请求，平均批大小 6.25（受 max_wait 超时影响，没每次都凑满 8）
    • VIP 平均延迟 34 步 < 所有请求平均 41.3 步，优先级调度生效
    • 4 节点分到 1/4/6/5 批，分布有偏差是因为批数少（16 批），key 多时偏差会更小

    6. 生产级实现¶

    6.1 vLLM¶

    vLLM（UC Berkeley 开源）是当前最流行的 LLM 推理框架，核心创新：

    • PagedAttention：KV cache 分页管理（类 OS 虚拟内存），解决 KV cache 内存碎片
    • Continuous Batching：动态批处理 + 请求可中途加入/退出
    • Priority Scheduling：支持请求优先级 + 抢占式调度
    • Multi-Worker：多 GPU 节点用 Ray + 一致性哈希路由

    对应本 demo： - PagedAttention → 队列（DynamicBatcher）的底层优化 - Continuous Batching → 队列的更激进版本 - Priority Scheduling → 堆（PriorityHeap） - Multi-Worker → 一致性哈希（ConsistentHashing）

    6.2 Triton Inference Server¶

    Triton（NVIDIA 出品）是生产级推理服务框架，核心特性：

    • Dynamic Batcher：本 demo 的 DynamicBatcher 的工业级实现，配置 max_batch_size + preferred_batch_size + max_queue_delay
    • Multiple Model Instances：同一模型多个实例并行，请求用轮询或一致性哈希分发
    • Model Ensembles：DAG 流水线（模型链），如 ASR → LLM → TTS
    • Priority Queues：支持请求优先级

    对应本 demo： - Dynamic Batcher → 队列（DynamicBatcher） - Model Ensembles → DAG（DependencyDAG） - Priority Queues → 堆（PriorityHeap） - Multiple Instances → 一致性哈希（ConsistentHashing）

    6.3 SGLang¶

    SGLang（UC Berkeley 出品，vLLM 后续）更进一步：

    • RadixAttention：用 Radix Tree 复用 KV cache（同前缀的请求共享 KV cache）
    • Structured Generation：约束解码（JSON/正则约束输出）
    • Multi-Modal：支持图像+文本输入

    RadixAttention 用 Radix Tree（一种 Trie 变体）管理 KV cache 复用，本质是用树结构表达 prompt 前缀的依赖关系，和 DAG 拓扑排序的思想相通。

    6.4 TensorRT-LLM¶

    TensorRT-LLM（NVIDIA 出品）是 TensorRT 的 LLM 专用版：

    • In-flight Batching：类 vLLM 的 continuous batching
    • Pipeline Parallelism：流水线并行（不同层分配到不同 GPU），用 DAG 决定层间依赖
    • Tensor Parallelism：张量并行（同一层的矩阵乘法切分到多 GPU）

    Pipeline Parallelism 的层间依赖就是本 demo 的 DAG 拓扑排序：第 k 层依赖第 k-1 层的输出，拓扑排序给出合法的层执行顺序。

    7. 调度策略的权衡¶

    7.1 吞吐量 vs 延迟¶

    • 批处理提高吞吐量但增加单请求延迟（要等凑批）
    • max_wait 是权衡旋钮：小 → 延迟低但批小（吞吐量低）；大 → 批大但延迟高
    • VIP 请求可以绕过批处理直接执行（牺牲吞吐量保延迟）

    7.2 公平 vs 优先级¶

    • FIFO 公平但无优先级（VIP 被阻塞）
    • 优先级堆保障 VIP 但可能饿死低优先级（后台请求永远排不上）
    • 解法：老化（aging）——等待时间长的低优先级请求自动升优先级

    7.3 均衡 vs 稳定¶

    • 取模哈希均衡但节点增减不稳定（80% 迁移）
    • 一致性哈希稳定但查归属稍慢（O(log n) vs O(1)）
    • 对 LLM 服务，稳定更重要（KV cache 迁移代价 >> 查归属开销）

    8. 监控指标¶

    生产级推理服务要监控的关键指标：

    指标 含义 对应数据结构
    QPS 每秒请求数 队列（批处理吞吐）
    P50/P99 延迟 请求延迟分位数 堆（优先级保障 P99）
    GPU 利用率 GPU 算力使用比例 队列（批处理提升利用率）
    批大小分布 每批的请求数分布 队列（DynamicBatcher）
    节点负载方差 各节点请求数的方差 一致性哈希（分布均衡度）
    迁移率 节点增减时 key 迁移比例 一致性哈希（O(k/n)）

    9. 总结¶

    LLM 推理服务调度是 4 种数据结构的协奏：

    • 堆 → 优先级调度（VIP/SLA 保障，19.9x 延迟优势）
    • DAG → 任务依赖（推理流水线拓扑排序，消除死锁/重做）
    • 队列 → 动态批处理（凑批提高吞吐量，3.33x 吞吐优势）
    • 一致性哈希 → 负载均衡（节点增减最少迁移，4x 迁移优势）

    生产级系统 vLLM、Triton、SGLang、TensorRT-LLM 底层都是这 4 种数据结构的不同实现与组合。理解了这 4 种数据结构的协作，就抓住了 LLM 推理服务调度的本质。
